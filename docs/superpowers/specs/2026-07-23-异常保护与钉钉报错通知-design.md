# 异常保护与钉钉报错通知 - 设计文档

日期：2026-07-23

## 背景与目标

用户需求：系统的所有方法/API 都要加异常保护，报错时通过钉钉通知，通知内容包含完整错误 traceback，且文案需告知这是"台账系统"。

项目规模约 44 个 .py 文件、700+ 函数（insurance/ 目录占 547 个），逐个包裹所有内部函数不现实，且会掩盖需要向上传播、由调用方感知的异常（违反最佳实践）。改为三层防护：

1. API 层全局兜底（覆盖所有 Flask 路由）
2. 后台常驻循环/队列消费者逐个保护（防止单次异常导致整个线程退出）
3. 定时脚本（crontab 独立执行）顶层保护（防止脚本崩溃后无人知晓）

三层出问题统一复用现有 `core/notify.py: notify_error()`，只增强这一个函数即可让全项目 15 处已有调用点自动带上 traceback，无需改动调用代码。

## 现状（调研结论）

- `core/notify.py` 已有完整的钉钉群机器人 webhook 推送封装（`DingTalkNotifier` + `notify_error()`），全项目约 15 处已手动调用，均在 `except` 块内、以字符串形式传入 `error`
- 全项目未发现 `import traceback` 用法，当前无任何地方记录/发送完整堆栈
- `insurance/api.py:479-482` 已有一个 `@insurance_bp.app_errorhandler(500)`，因非 blueprint-scoped 实际对整个 Flask app 全局生效，但不含 traceback，且 `web/api.py`、`callback/server.py` 未见等效兜底
- API 响应约定统一为 `jsonify({"code": xxx, "msg": "..."})`
- 8 处长期运行的常驻 daemon 线程/循环（见下表），未见统一的定时任务框架（schedule/APScheduler），定时任务通过外部 crontab 调用独立脚本实现
- `main.py` 用 `app.run(debug=True, threaded=True)` 启动，未见 gunicorn 命令行调用但代码注释提到实际部署可能用 `gunicorn -w 2`；全仓库无 SIGTERM/SIGINT 优雅停机处理

## 架构

```
异常发生
  → except 块捕获
    → logger.error(..., exc_info=True)   # 本地日志
    → notify_error(module, method, error, detail)   # 增强后自动带 traceback
      → sys.exc_info() 判断是否在异常上下文
      → traceback.format_exc() 截断最后 40 行
      → 拼装 Markdown（含"台账系统"标识）
      → DingTalkNotifier.send()（异步线程，15分钟同标题去重）
```

## 组件设计

### 1. `core/notify.py` — `notify_error()` 增强

函数签名不变：`notify_error(module: str, method: str, error: str, detail: str = "")`，完全向后兼容现有 15 处调用。

内部新增：

```python
import sys, traceback

tb_text = ""
if sys.exc_info()[0] is not None:          # 仅在 except 块内调用时才有堆栈
    tb = traceback.format_exc()
    lines_tb = tb.strip().splitlines()
    if len(lines_tb) > 40:                  # 截断保护，避免钉钉消息过长
        lines_tb = ["... (已截断，仅显示最后40行) ..."] + lines_tb[-40:]
    tb_text = "\n".join(lines_tb)
```

消息格式：

```
标题: ⚠ 台账系统 - {module} 异常
正文:
### ⚠ 台账系统异常告警
- **系统**: 台账系统
- **时间**: {ts}
- **模块**: {module}
- **方法**: `{method}`
- **错误**: {error[:500]}
- **详情**: {detail[:500]}   # 若有

**堆栈信息**:
```
{tb_text}
```
```

去重规则不变：沿用 `title`（不含 traceback）15 分钟内去重，避免同一错误反复刷屏但仍能触发通知。

### 2. API 层全局异常兜底

`main.py` 新增：

```python
@app.errorhandler(Exception)
def _handle_uncaught_exception(error):
    logger.error("未捕获异常: %s", error, exc_info=True)
    notify_error("Web服务", request.path, str(error), f"method={request.method}")
    return jsonify({"code": 500, "msg": "服务器内部错误"}), 500
```

- 覆盖 `web/api.py`、`insurance/api.py`、`callback/server.py` 所有蓝图路由
- 删除 `insurance/api.py:479-482` 现有重复的 `@insurance_bp.app_errorhandler(500)`，避免同一异常触发两次通知
- 各路由函数内部已有的局部 try/except 保持不变，不受影响（兜底只捕获路由函数内部没接住、意外冒出来的异常）

### 3. 后台常驻循环保护

给以下 8 处循环体补上"每轮/每个任务 try/except 包裹，异常时记录 + notify_error + continue，不让线程退出"（若已有等效保护则跳过，实现阶段逐个确认现状再决定是否需要改动）：

| 文件 | 函数 | 说明 |
|---|---|---|
| `core/fetcher.py` | `_worker` / 主循环 | 消息拉取 |
| `main.py` | `_stuck_processing_watchdog` | 卡死自愈看门狗 |
| `core/contacts.py` | `_worker` | 通讯录同步 |
| `insurance/handler.py` | `_consume` | 保单识别队列 |
| `insurance/ai_checker.py` | `_consume` | AI核对队列 |
| `quote/handler.py` | `_consume` | 报价队列 |
| `quote/matcher.py` | `_timeout_loop` | 超时匹配循环 |
| `insurance/fill_pending.py` | `_scan_loop` | 补录扫描循环 |

一次性任务线程（`do_fetch`、批量下载、数据回填等）不在本次强制范围内——这些通常已有局部 try/except，且一次性失败不会导致常驻服务整体挂掉。

### 4. 定时脚本保护

`renewal_task_scan.py`、`policy_expiry_reminder.py`、`task_group_sync.py`、`task_contact_sync.py` 的 `main()` 顶层加：

```python
if __name__ == "__main__":
    try:
        main()
    except Exception as e:
        logger.error("脚本执行异常: %s", e, exc_info=True)
        notify_error("定时任务", "脚本名.main", str(e))
        sys.exit(1)
```

## 数据流

1. 任意受保护位置（API 路由 / 后台循环 / 定时脚本）发生未预期异常
2. `except` 块捕获，写本地日志（`logger.error(..., exc_info=True)`）
3. 调用 `notify_error(module, method, error, detail)`（签名不变）
4. `notify_error` 内部通过 `sys.exc_info()` 自动采集当前 traceback，截断后拼入 Markdown 正文，标题/正文标注"台账系统"
5. 异步线程发送到钉钉群机器人（`config.yaml` 中 `notify.webhook_url` / `notify.secret`），15分钟同标题去重
6. API 层同时向前端返回统一 JSON 错误响应；后台循环 continue 继续下一轮；定时脚本记录后 `sys.exit(1)`

## 错误处理边界

- **不改变**已有的局部 try/except 逻辑和业务侧的错误处理/降级逻辑（如百度 OCR 兜底、SDK 重试等），只在其"最终兜不住时"的最外层补一道网
- **不**对 insurance/policy_parser.py 等内部字段提取函数做逐个包裹，避免异常被吞掉导致调用方拿到不完整数据而不自知
- gunicorn 多 worker 场景：每个 worker 会各自运行常驻线程，异常通知可能来自不同 worker，属正常现象，沿用现有进程内去重即可，不做跨 worker 去重

## 测试计划

- 单元验证：手动触发 `notify_error()` 在 except 块内 / 块外两种场景，确认 traceback 是否正确附加/为空
- API 层：本地起服务，构造一个会抛异常的路由（如访问不存在的记录 ID 触发内部异常路径），确认全局 errorhandler 捕获、返回 JSON、钉钉收到含 traceback 的通知
- 后台循环：本地 mock 一次异常（如临时修改逻辑强制抛错），确认线程不退出、下一轮正常执行、钉钉收到通知
- 回归：确认现有 15 处 `notify_error` 调用点行为不变（仅多了 traceback 字段），15 分钟去重仍生效
- `run_ocr.py` 同步检查：按 CLAUDE.md 要求，`main.py` 新增的 errorhandler 若涉及初始化差异需同步确认 `run_ocr.py` 是否也需要注册（本地开发环境无 SDK 但仍有 Flask 路由）
