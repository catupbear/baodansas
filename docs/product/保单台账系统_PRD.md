## 一、背景与问题

### 1.1 行业背景

车险经代/代理公司的核心业务流程是：向保险公司出单 → 保司回传保单PDF（通常经企业微信群转发）→ 业务员整理台账（保单号、车牌、投保人、保费、佣金等字段）→ 用于对账、结算提成、到期续保跟进。这套台账目前行业内普遍靠人工在Excel里手工誊抄完成。

### 1.2 现状与核心问题

| 问题 | 具体表现 | 影响 |
|---|---|---|
| 抄录效率低 | 一份保单PDF需人工识别、誊抄十几到几十个字段 | 业务员大量时间耗在录入而非展业 |
| 抄录易出错 | 人工誊抄保费、佣金率等数字类字段出错率高 | 对账错误、提成算错、引发内部纠纷 |
| 台账分散、无归属 | 台账散落在各员工Excel里，企业管理者无法看到全局数据 | 员工离职带走客户资料、企业无法沉淀数据资产 |
| 续保依赖人工记忆 | 无系统化提醒机制，业务员凭经验/备忘录跟进到期保单 | 到期未跟进，客户流失至竞对 |
| 各保司PDF格式不统一 | 40+家保司保单排版差异极大，人工需分别熟悉 | 新人上手成本高，跨保司台账口径不统一 |

### 1.3 解决方案价值主张

依托企业微信"会话存档"能力（Finance SDK），业务员只需将保单PDF转发到指定的服务群，系统即自动：**下载 → OCR/文本提取 → 按保司规则解析字段 → 归属到对应员工 → 写入台账 → 按需同步到钉钉多维表 → 到期前自动提醒续保**。企业管理者获得统一的企业级台账视图、经营看板与员工归因数据。

### 1.4 现状说明（重要）

本系统**已完成开发并上线运行**，本PRD是在现有实现基础上做的完整需求梳理，作用是：
1. 给团队一份准确、无歧义的功能范围基线文档；
2. 暴露当前实现中的边界问题、半成品功能、待确认口径（见第十一章）；
3. 作为后续迭代排优先级的依据。

因此本文既包含"需求"也包含"现状盘点"，第九章会明确区分"已实现"与"待完善/待决策"。

## 二、术语表

| 术语 | 含义 |
|---|---|
| 台账 / 保单台账 | 系统中保单识别记录的列表数据，等价于传统人工维护的Excel保单登记表 |
| 监控群 | 被配置为"自动识别"的企业微信群或私聊，群内PDF会被系统自动抓取识别 |
| 归属 | 一条保单记录被判定属于哪个员工（user_id）、哪个企业（enterprise_id） |

| 互补/合并显示 | 同一车牌/车架号/同一份PDF的多条记录之间互相补全缺失字段后展示 |
| 异常记录 | 系统按10个核心必填字段自动判定"关键信息缺失"的记录 |
| 字段配置模板 | 用户/企业/全局三级作用域的展示列、导出列、别名、日期格式、计算公式配置集合 |
| 企业 | 使用本系统的客户单位（保险经代公司），对应系统内的enterprise实体 |
| 超级管理员（超管） | 平台运营方（午虎团队）账号，可管理所有企业与全局配置 |
| 企业管理员 | 客户企业的管理者账号，管理本企业员工与配置 |
| 员工 | 企业管理员名下的一线业务员账号 |

### 3.2 用户画像

**画像一：企业管理员 —— "老张"，某车险经代公司负责人**
- 背景：管理10-30人的业务团队，公司靠车险佣金和续保率盈利。
- 痛点：看不到员工手上到底有多少保单、多少快到期，年底对账靠员工各自报数，经常对不上。
- 期待：有一个统一后台，能看到全公司的台账、经营数据，能设置自己公司习惯的字段口径（别名、佣金计算公式），出问题能追溯到是谁的单子。

**画像二：一线业务员 —— "小周"，展业3年**
- 背景：每天在多个微信群和保司/客户对接，手头保单几十到上百份。
- 痛点：抄单据枯燥且容易出错，续保靠自己拿小本本记日期，经常忘。
- 期待：发个群消息就自动记账，续保系统能提醒自己，不用自己记。

**画像三：平台运营方（超管）—— 午虎团队客户成功/技术支持**
- 背景：同时服务多家客户企业，需要保证识别质量、处理新保司接入请求、答疑。
- 痛点：新保司源源不断，需要持续维护解析规则；客户反馈的识别错误需要快速定位修复。
- 期待：有异常监控、报错反馈闭环、全局数据看板，能提前发现问题而不是等客户投诉。

### 3.3 核心用户故事

- 作为**业务员**，我希望把保单PDF转发到服务群后，台账里自动就有这条记录，这样我不用再手动录入。
- 作为**业务员**，我希望系统在保单到期前提醒我，这样我不会错过续保时机。
- 作为**企业管理员**，我希望能看到公司所有员工的台账汇总，这样我可以掌握公司整体业务量和续保情况。
- 作为**企业管理员**，我希望能自定义佣金计算公式，这样导出的台账能直接用于结算，不用二次加工。
- 作为**员工**，我希望识别错误的字段能自己手动改正，这样台账数据始终是准的。
- 作为**超管**，我希望系统在遇到没见过的保司时能告诉我，这样我可以及时补充解析规则。

## 四、产品目标与成功指标

### 4.1 北极星指标（建议）

**月度"有效台账记录数"占该企业总识别量的比例**（有效 = 非异常 + 已核对/已人工修正），衡量系统真正能被客户直接使用而非需要大量人工二次加工。

> 当前无历史基线数据，建议上线埋点统计首月数据后确定目标值，本PRD暂不给出具体数字，避免拍脑袋定指标。

### 4.2 分层指标

| 层级 | 指标 | 说明 |
|---|---|---|
| 效率 | 单份保单从"发到群"到"台账可见"的平均耗时 | 目标应控制在数十秒级（受OCR引擎响应时间影响） |
| 效率 | 单份保单人工核对/修正耗时 | 对比人工全程抄录耗时，量化效率提升 |
| 质量 | 关键字段识别准确率（抽样质检口径，见 `/qc` 技能） | 按保司分层统计，识别新增/劣化保司 |
| 质量 | 异常记录占比 | 关键字段缺失比例，越低说明解析规则覆盖越全 |
| 留存 | 企业月活跃度（月识别量>0的企业占比） | 判断客户是否持续在用 |
| 商业化 | 标准版→企业版套餐升级率 | 配额触顶（3000次/月）后的转化情况 |
| 续保 | 续保任务转化率（won/总任务数） | 衡量续保CRM模块的实际业务价值 |
| 稳定性 | OCR引擎熔断次数、失败率 | 火山/百度双引擎降级监控 |

## 五、整体方案概览

### 5.1 自动识别主流程

```
业务员在企业微信群/私聊发送保单PDF
  → 企微会话存档(Finance SDK) 增量拉取消息
    → 命中"监控群"配置？
        否 → 忽略
        是 → 按 sender 查员工绑定，确定归属(user_id/enterprise_id)
            → 校验企业套餐配额（超额静默丢弃并记日志）
            → 下载PDF → 计算文件MD5判重
                同msg_seq → 标记 duplicate（跳过）
                不同msg_seq同MD5 → 直接复制已有识别结果（省OCR成本）
                全新文件 → 上传COS → OCR识别
                    pdfplumber文本提取 → 质量不佳降级火山OCR → 再降级百度OCR
                    → policy_parser 按保司规则解析字段（一份PDF可拆分出多份保单）
                    → 字段互补（同车牌/同车架号/同PDF内互相补全）
                    → 写入台账（insurance_records + insurance_policy_fields）
                    → 自动判定异常（10项核心字段缺失检测）
                    → 按监控配置自动同步钉钉多维表（若已配置）
                    → 未识别出保司 → 钉钉告警提示新保司接入需求
```

### 5.2 手动上传流程

企业管理员/员工在网页端"手动上传"页直接拖拽PDF/图片，系统走同样的OCR+解析+互补链路，落库后立即可在台账中查看、编辑、导出。

### 5.3 台账查看与治理

台账列表支持极其丰富的筛选（群、发送人、保司、险种、车牌、日期区间等）、去重显示、按车牌合并显示、异常记录人工复核（手动补录/标记正常）、导出Excel（含合并导出、活公式导出）、批量重新识别、批量同步钉钉、批量下载原文件。

### 5.4 续保管理（下游消费台账数据的CRM模块）

系统每日巡检台账中的保单到期日期，聚合成以"车牌/车架号"为客户主键的续保任务，按到期紧迫度自动定优先级，业务员可在续保Tab里跟进、记录跟进历史、标记成交/流失；同时每日向对应群推送到期提醒消息（企业微信FlowBot机器人）。

## 六、功能需求详述

### 6.1 消息自动识别与入账

- 支持监听指定企业微信群/私聊，识别其中的PDF保单附件（图片暂不支持自动识别，仅手动上传支持图片）。
- 归属判定优先级：**sender精确绑定 > 监控配置默认归属**。
- 同一份PDF被不同人/不同时间重复发送：按文件MD5判定，避免重复OCR开销，同时保留每次发送的独立记录（用于台账追溯"谁发了这份文件"）。
- 一份PDF内含多份保单（如交强险+商业险+驾意险同文件）：自动拆分为多条独立记录，并互相补全共同字段（车牌、投保人等）。
- 企业套餐超出月度识别配额时，自动识别消息**静默丢弃**（不入库、不提示发送人），需要产品决策：是否应改为提示"本月额度已用尽"而非静默失败，避免客户以为系统故障（见第十一章开放问题）。

### 6.2 保单台账（核心模块）

**筛选能力**：来源、群名、发送人、保司简称、险种类型、状态（成功/需人工补充/非保单/失败）、核对状态（仅超管）、车牌/保单号/投保人/被保人/业务员关键词搜索、签单/起保/终保日期区间、更新时间区间、企业（仅超管代管）。

**列表呈现**：
- Tab切换：全部 / 成功 / 需人工补充（异常） / 非保单 / 失败，各Tab计数与筛选条件联动一致，避免"数字对不上"的体验问题。
- 支持"去重显示"开关：同一天同保单号只显示最新一条。
- 支持"按车牌合并显示"：企业可设置默认开启，车牌相同的多条记录（如交强+商业+驾意）合并为一行按险种分列展示。
- 单条记录操作：预览、编辑字段、标记正常/撤销、内部备注（仅超管）、重新识别、同步钉钉、删除（仅超管，软删除）、报错反馈。
- 批量操作：批量导出、批量重新识别+同步、批量下载原文件（≤1000条/次，超限提示分批）。

**详情/预览**：左右分屏，左侧原文件（PDF/图片），右侧三个可切换面板——"查看列表信息"（可编辑）、"查看原文"（OCR文字，供逐项核对）、"重新识别"。多保单文档支持在预览内切换查看其他保单。手动编辑字段后会打标记（橙色圆点），供追溯"哪些是系统识别、哪些是人工改过"。

### 6.3 异常检测与人工复核

- 系统按10个核心字段（承保公司/保单号/险种/车牌/投保人/被保人/签单日期/起保日期/终保日期/保费）自动判定，任一缺失即标记"需人工补充"，用红/黄标签在列表中提示。
- 人工处理路径：① 直接在列表内联编辑补录缺失字段；② 若确认该保单本身就不含某字段（如无需车船税），可"标记为正常"并填写理由，避免被反复当作异常提示；③ 可撤销标记。
- 超管另有"内部管理备注"通道，用于记录问题归因（我方待处理/我方已修复/客户侧问题），与客户可见的复核流程分离。

### 6.4 手动上传识别

- 支持PDF/JPG/PNG，支持拖拽或点击选择，支持多选批量上传。
- 上传后展示文件卡片（PDF红色图标/图片绿色图标），支持单个删除/清空重选。
- 点击"开始识别"后逐个处理，可选"上传保单到云存储"开关决定原文件是否留存COS。
- 识别结果与自动识别记录共用同一套展示/编辑/导出逻辑。
- 需遵循企业套餐月度配额限制，超额时禁止继续识别并提示原因（欠费/未配置套餐/超额度三种情形需分别给出清晰文案，当前部分情形是否已有明确前端提示需与研发确认）。

### 6.5 字段配置中心

统一入口"系统设置"，六个子功能：

1. **别名设置**：为保司全称、险种全称配置企业/个人习惯的简称，历史数据配置后自动按新别名展示（不改变底层数据）。
2. **日期格式**：签单/起保/终保日期可分别或统一设置展示格式（YYYY/MM/DD等5种预设）。
3. **自动计算公式**：按"承保公司+险种"维度配置佣金/公司利润/跟单利润等衍生字段的计算公式（四则运算，基于保费/车船税/佣金率/采购费率等原始字段），公式合法性校验+示例预览。
4. **页面列配置**：控制台账列表展示哪些列、顺序如何。
5. **导出列配置**：控制导出Excel包含哪些列、顺序如何，与页面列配置相互独立。
6. **备注快捷选择**：预置常用备注文案池，支持按经办人/保司/险种/关键词筛选候选备注，支持Excel批量导入选项池。

**模板与作用域机制**：
- 三级作用域：全局默认 / 企业级 / 个人级，企业管理员可将企业模板设为"对员工可见"，员工可选择使用企业模板或维护自己的私有模板，互不覆盖。
- 支持保存多套模板并随时切换启用哪一套。
- 重置列配置时，系统自动把当前配置备份为一个带时间戳的新模板，避免误操作导致配置丢失。

### 6.6 导出与批量操作

- **导出Excel**：弹窗勾选需要导出的字段（默认沿用用户的导出列配置），支持"成功记录完整导出"/"失败记录（文件名+失败原因）"/"非保单文档（文件名+类型）"三种导出类型。
- **按车牌合并导出**：车牌相同的记录合并为一行，公共字段（承保公司/车牌/投保人等）取值互补，险种相关字段（保单号/保费/佣金等）按商业险/交强险/非车险分别列出。
- **活公式导出**：用户在"自动计算公式"里配置的公式，导出时会转换为Excel真实单元格公式（而非计算好的静态值），客户打开Excel后修改保费等原始值，佣金等衍生列会自动重算，即"表格是活的"，这是本系统相对纯人工Excel台账的一个显著体验优势，应作为对外宣传卖点。
- **批量下载原始文件**：勾选记录后打包ZIP下载（≤1000条/次）。
- **企业经营报告**：面向企业管理员的汇总报表（识别量、保司/险种分布、员工上传排名、每日趋势图），支持导出Excel或生成**免登录分享链接**（用于展示给企业老板或客户，链接经签名防止随意猜测遍历查看其他企业数据）。

### 6.7 钉钉多维表同步

- 支持按"监控群配置"或"手动同步目标"绑定钉钉多维表格的具体base/sheet，系统自动解析钉钉分享链接得到目标ID，免去客户手工填写。
- 同步字段映射可按客户需求做差异化配置（即客户钉钉表格里的列名可以跟系统内部字段名不同）。
- 同步逻辑为"存在则更新、不存在则插入"（按保单号查重），支持自动为钉钉表格创建缺失字段列。
- 触发方式：自动识别完成后自动同步 / 单条手动同步 / 批量手动同步 / 批量重新识别时顺带同步。

### 6.8 数据看板（超级管理员）

- 总览：总量/成功/失败/异常/待处理、今日/近7天趋势。
- 保司识别量排行、险种分布、OCR引擎使用分布、消息来源分布（群/私聊/手动上传）、各企业使用量排行。
- 折线图展示识别趋势（按小时/按天自动切换粒度）。
- 当前仅超管可见，企业管理员看不到本企业维度的看板（可作为后续增值功能开放给企业管理员，见路线图）。

### 6.9 续保管理

- 系统每日巡检台账中即将到期（未来30天内）及已过期不久（过去30天内，用于跟进流失挽回）的保单，按"车牌优先/车架号兜底"聚合为客户维度的续保任务。
- 任务默认按到期紧迫度自动定优先级（7天内/30天内/其余），默认跟进人取该客户最新保单的原始发送人（业务员）。
- 员工需自助开启"续保功能"后，自己名下的保单才会被纳入扫描——这是产品有意设计的渐进式开放（避免强推功能给不需要的用户），但也意味着未开启的员工的续保任务是"看不见"的，需要在使用手册/新手引导中明确告知，否则用户会误以为系统没有识别到到期保单。
- 每日到期提醒通过企业微信FlowBot机器人推送到原保单所在群，@对应跟单人，并附带免登录深链直达该续保任务详情。
- 已标记"成交/流失"的任务不会被后续巡检覆盖（尊重人工处理结果），超期30天未处理的任务自动标记过期。

### 6.10 用户与企业管理

- 手机号+密码登录，支持自助注册（短信验证码）+ 待管理员激活的门槛机制（未激活账号可登录看列表但不能执行OCR/同步等操作）。
- 企业管理员可管理本企业员工（增删改查、重置密码）。
- 超管可管理所有企业、配置套餐类型与配额、查看/审批企业信息收集问卷（面向潜在客户的免登录问卷链接）。
- 企业套餐：标准版（3000次/月识别配额）、企业版/企业试用版（不限额），支持"下一套餐到期自动切换"排队机制。

### 6.11 客户支持与反馈闭环

- 使用手册：登录即可查看（含未激活/潜在客户），仅超管可编辑与插图。
- 报错反馈：任意记录可提交报错，转发至内部钉钉群，供技术人员快速定位修复。
- 经营报告分享页也支持匿名反馈入口，方便面向最终客户展示时收集意见。

## 七、非功能需求

| 类别 | 要求 | 现状/依据 |
|---|---|---|
| 性能 | 单次导出/批量下载需设行数上限，避免网关超时 | 已实现：导出≤3000行相关限流、批量下载≤1000条 |
| 性能 | 统计类查询需专用索引，避免扫描大字段拖慢响应 | 已实现覆盖索引，统计查询从1.25s降至0.14s |
| 可靠性 | OCR引擎需支持自动降级，避免单一引擎故障导致识别全面失败 | 已实现火山→百度双引擎熔断降级机制 |
| 可靠性 | 数据库连接异常需有重试保护，避免误清空归属数据 | 已实现（历史事故后补充的保护逻辑，见第十一章） |
| 安全 | 企业间数据严格隔离，任何跨企业查询需仅限超管角色 | 已实现enterprise_id过滤，需持续做权限穿透测试 |
| 安全 | 免登录分享链接（经营报告等）需防止被遍历/猜测 | 已实现签名机制，建议定期审计签名强度与有效期策略 |
| 安全 | 默认管理员账号需在部署后强制修改初始密码 | **现状为固定弱密码 admin/admin123，存在安全隐患，需在部署流程/PRD中明确整改要求** |
| 合规 | 保单含身份证号、车主姓名等个人信息，需评估存储加密与访问日志要求 | 现状未在调研中确认是否有专门的敏感字段加密/脱敏机制，需要与法务/安全团队确认合规要求 |
| 可用性 | 关键操作失败需有清晰提示文案，不能静默失败 | 部分场景（配额超额的自动识别）当前为静默丢弃，需产品决策是否需要主动告知 |

## 八、边界与非目标（Out of Scope）

1. **预报价系统（`quote/`模块）不在本次台账系统范围内。** 该模块对接外部平台 riskapi.wuhuxiche.com，处理行驶证/身份证OCR配对与报价提交，与台账系统的数据模型、绑定关系（`user_sender_binding`）完全独立、互不共享。若未来产品方向是打通"识别到保单→提醒续保→自动生成报价"的完整链路，需要单独调研外部平台接口并重新立项。
2. **保司解析规则的自动学习/模板训练**（代码中的 `template_train_records`、`registry.json`）当前状态不明确（有数据结构但未发现完整的训练触发链路），本期不作为承诺交付的功能，需先与研发确认完成度。
3. **历史数据默认不回填**：新增解析字段/修复解析bug后，已入库的历史记录默认不会被重新解析，除非发起专项回填任务。
4. **企业管理员/员工暂不开放数据看板**：当前看板仅超管可见，企业级看板需求需另行评审（例如是否要包装为面向客户的付费增值功能）。

### 9.1 已实现（P0，已上线）

### 9.2 建议P1（体验与商业化完善，非新增大功能）

| 事项 | 理由 |
|---|---|
| 配额超额时的用户提示优化 | 当前自动识别静默丢弃，客户体验为"系统没反应"，应改为主动提示或至少日终汇总通知 |
| 企业管理员开放"轻量看板" | 已有超管看板的数据基础，包装为企业自己可见的经营视图，提升企业管理员日常打开频次 |
| 续保功能开启引导 | 当前"员工需自助开启"容易被误解为系统未识别到到期保单，建议增加首次进入续保Tab的引导提示 |
| 默认管理员密码整改 | 安全基线问题，建议部署脚本层面强制改为随机初始密码或首次登录强制改密 |
| 敏感信息合规评估 | 明确身份证号等PII字段的存储、访问、脱敏策略 |

### 9.3 建议P2（需要产品决策后再排期）

| 事项 | 理由 |
|---|---|
| 模板自动训练/新保司自动发现 | 需先确认现有半成品代码的完成度和产品价值，可能是"降低新保司接入人力成本"的高价值方向 |
| 台账系统与预报价系统数据打通 | 潜在价值是"识别到保单→自动生成续保报价"，但涉及独立外部系统调研，成本较高 |
| 企业级看板商业化 | 可探索作为企业版套餐的差异化卖点 |

## 十一、风险与开放问题

1. **"支持50+保司"的对外宣传口径与代码实际情况（约38家精确规则+约27组特征兜底）存在差异**，建议与研发确认当前稳定支持（识别量达标阈值判定）的保司数量，统一对外宣传口径，避免客户预期落差。
2. **模板自动训练/发现机制**（`template_train_records`/`registry.json`）状态不明，需确认是完整功能、半成品还是遗留实验代码，避免误列入已交付范围。
3. **默认超级管理员账号 `admin/admin123`** 属于已知安全隐患，建议列为P1安全整改项。
4. **配额超额静默丢弃消息**：当前体验是客户不知道识别为何"没反应"，需产品决策改进方案（提示 vs 静默，是否收费提醒等）。
5. **续保功能默认关闭（需员工自助开启）**：需明确这是否符合产品预期的渐进式设计，还是应该改为企业管理员统一开启、员工可选择退出。
