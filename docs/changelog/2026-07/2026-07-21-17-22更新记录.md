# 数据来源标签区分互补来源

## 需求说明

「列表信息」面板的字段数据来源标签（仅超管可见）此前只区分 AI质检识别 / 手动修改 / PDF提取 / OCR提取。
但很多字段值并非从本单 PDF 提取，而是来自互补逻辑（同车牌历史保单、同 PDF 兄弟保单、文件名、系统关联等），
标签统一显示「PDF提取」会误导排查。本次为互补来源的字段显示具体来源标签：

- **同车牌互补** / **同车架号互补** / **按人名互补** — 跨保单字段互补（识别时落库）
- **同PDF互补** — 同一 PDF 多保单/兄弟记录互补（识别时落库 + 详情接口运行时）
- **文件名提取** — 车牌从文件名兜底提取（详情接口运行时）
- **系统关联** — 跟单人由发送人绑定用户实时关联（详情接口运行时）

标签优先级：AI质检识别 > 手动修改 > 互补来源 > 记录识别引擎（PDF提取/OCR提取）。

## 实现方案

互补写入点统一调用新增的 `mark_filled_source(fields, 字段名, 来源)`，
将来源记入 `parsed_fields["_filled_sources"]`（`{字段名: 来源}`）：

- 随 parsed_fields 一起落库，无需数据库变更；重新识别生成全新 parsed_fields，标记自动重置
- 反向回填历史记录时标记同样写入对方记录的 parsed_fields，随既有更新一起保存
- 详情接口 `GET /api/insurance/records/<id>` 返回新增字段 `field_sources` =
  落库标记 + 该接口运行时互补（跟单人/兄弟记录/文件名/同车牌）的合并结果，键为 OCR 字段名或导出列名
- 下划线开头的内部键不参与字段映射透传、合并导出透传、前端「解析字段」弹窗展示

存量记录无落库标记，标签行为不变（仍按引擎显示）；运行时互补与跟单人关联对存量记录同样生效。

## 数据库变更

无（标记存于 parsed_fields JSON 内部键 `_filled_sources`）。

## 代码变更

| 文件 | 变更 |
|------|------|
| `insurance/handler.py` | 新增 `mark_filled_source()`；`_cross_fill_same_pdf` / `_apply_cross_fill`（正向+反向）/ `_cross_fill_by_person`（正向+反向）所有写入点打标记 |
| `insurance/api.py` | `_cross_fill_from_siblings` 打标记；详情接口收集运行时互补来源并返回 `field_sources`；恢复识别值时清除对应字段标记；合并导出透传排除下划线内部键 |
| `insurance/field_mapping.py` | `apply_mapping` 透传自定义字段时排除下划线开头内部键，防止 `_filled_sources` 泄漏进 mapped/display 字段 |
| `web/templates/insurance.html` | `fieldSource()` 增加互补来源分支（青色标签，文本为具体来源）；新增 `publicFields()` 过滤内部键，解析字段弹窗改用其遍历 |

## 兼容性

- 历史 API 兼容：`field_sources` 为详情接口新增字段，旧前端忽略即可；parsed_fields 新增内部键已在映射/导出/展示三处排除
- 手动修改 / AI质检 标签优先级高于互补，互补字段被手动改后标签自动切换为「手动修改」
- 「恢复识别值」会同步清除该字段的互补标记

## 部署步骤

1. 上传以下文件到服务器 `/home/wxbot/` 对应路径：
   - `insurance/handler.py`

   - `web/templates/insurance.html`

3. `kill -HUP` 平滑重载 gunicorn
