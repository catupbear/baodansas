# 2026-07-24 16:53 更新记录

## 需求说明

排查发现：定时任务的群同步（`task_group_sync.py`）不会把「存量识别群」自动加入监控配置。

**根因**：识别群自动匹配（`insurance/auto_monitor_match.py`）上线于 2026-07-22，而群同步逻辑里
`check_and_sync_group` 的调用被放在 `if name_changed:`（群名相对数据库旧值发生变化）分支内。
于是——

- 自动匹配上线**前**就已存在、之后群名**再没变过**的识别群，`name_changed` 恒为 False，
  即使每 6 小时的全量刷新重新拉取群名，也永远不会触发自动匹配 → 一直不进监控配置。
- 只有新发现群（群名从「空 → 实名」）或群名被改动的群才会被捞到。

事件回调侧（`callback/event_callback.py`）同样只在 `name_changed` 时触发，逻辑一致。

Dry-run 实测：全表 310 个群中命中「识别群 + TZ编号」规则 41 个，其中 **40 个存量识别群从未进入监控配置**。

## 数据库变更

无表结构变更。回补动作只向 `monitor_configs.rooms` 追加群成员（走既有幂等入口，判重后追加）。

## 代码变更

### 1. `task_group_sync.py`（长效修复）

`run_sync` 的每群处理，在「同步成功（群名未变）」的 else 分支中新增：全量刷新（`full=True`）时
也对识别群做一次 `check_and_sync_group` 幂等补齐。

- 挂在 `full`（而非仅 `force`）上：进程启动的强制全量 + 每 6 小时例行全量都会自动补齐存量，
  不必等群名变化或进程重启。
- 增量同步（`full=False`）保持轻量，不触发。
- `check_and_sync_group` 内部判重且吞异常，重复调用安全、不中断同步循环。

### 2. `backfill_monitor_match.py`（新增，一次性回补脚本）

用于「不想等下一轮全量、要立即补齐存量」的场景。

- 默认 dry-run（只读）：扫全表列出「将加入 / 已存在 / 需建占位企业」的识别群清单，不写任何库。
- `--apply`：对待加入的群调 `check_and_sync_group` 实际写库（复用线上幂等逻辑）。
- 规则常量直接复用 `auto_monitor_match`，避免与线上判定漂移。

## 部署步骤

> ⚠️ 本次改动尚未部署。以下操作会改变服务器运行状态，须经确认后执行。

1. 上传 `task_group_sync.py` 到服务器项目目录。
2. **重启群同步进程**（`task_group_sync.py` 是独立进程，与 web 服务解耦）——重启后启动即跑一次
   强制全量，会自动补齐这批存量识别群；之后每轮全量持续兜底。
   - 若不重启，也可在服务器项目根执行 `python3 backfill_monitor_match.py`（先看 dry-run 清单）
     再 `--apply` 立即补齐，无需动进程。

## 补充（同日增强）：识别群补齐汇总日志

诉求：日志里「同步成功」看不到补齐判断（判重命中是静默 return），无法直观确认逻辑生效。

- `insurance/auto_monitor_match.py`：`check_and_sync_group` 增加返回状态
  （`None`=非识别群 / `already`=已在配置 / `added`=本次新增 / `error`=异常）。
- `task_group_sync.py`：`run_sync` 累计本轮各识别群处理结果，同步结束后打印一条汇总：
  `强制全量刷新识别群补齐: 命中 N | 新增 X, 已在配置 Y, 异常 Z`（命中数为 0 时不打）。

以后每轮全量都能一眼看到识别群补齐的判断执行情况，无需反查数据库。
