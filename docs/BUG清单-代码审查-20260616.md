## 🔴 一、数据越权 / 安全

### [ ] A1. 会话存档媒体接口完全无鉴权 ✅🔴
- **位置**：`web/api.py:79-81`
- **问题**：`before_request` 显式跳过 `/api/media/` 的 JWT 校验（注释称"监控页面通过 session 访问"，但该接口并不校验任何 session/token）。
- **影响**：无需登录，顺序枚举 `GET /api/media/1、2、3…`（seq 自增）即可下载**所有企业**的存档媒体（图片/语音/视频/保单 PDF/身份证图）。
- **建议**：对 `/api/media/` 加登录校验并按企业/绑定关系做归属校验；媒体用 `<img src>` 无法带 header 的场景改用短时一次性签名 URL，不要用可枚举 seq 作唯一凭证。

### [ ] A2. 保单记录跨企业越权（IDOR） ✅🔴
- **根因**：`insurance/db.py:1646` `get_insurance_record` 仅 `SELECT * FROM insurance_records WHERE id=%s`，无 enterprise_id/user_id 过滤。
- **受影响端点**（`insurance/api.py`，均按 record_id 操作、无归属校验）：
  - 读：`get_record`(812)、`get_record_raw_text`(1199)、`preview_record_file`(1160)
  - 改：`update_record_fields`(999)、`mark_record_normal`(1094)、`undo_mark_record_normal`(1119)、`reupload_reocr`(2075)、`reocr_record`(2166)
  - 删：`retry_record`(1999，**物理 DELETE** at 2054，绕过"仅超管软删")
  - 批量：`batch_reocr_sync`(2537)、`batch_sync_dingtalk`(3421)、`sync_record_to_dingtalk`(2459)
- **影响**：任意登录用户枚举 record_id 即可读取/篡改/删除/导出任意企业的保单（含投保人身份证号、车牌、地址、保单号），甚至把他人记录批量同步到攻击者自己的钉钉表。
- **建议**：`get_insurance_record` 增加 enterprise_id/user_ids 过滤参数；所有按 record_id 的端点统一调用带归属过滤的版本。可一次性消除大部分 IDOR。

### [ ] A3. 消息查询疑似不按企业过滤 ⚠️🔴
- **位置**：`web/api.py:110-202`（`/api/conversations`、`/api/messages`）+ `storage/db.py:306-382` `query_messages`
- **问题**：`before_request` 只校验"登录+启用"，不区分角色/所属企业；查询把前端 `corpid`/`roomid`/`sender` 直接透传，`query_messages` 无 user/enterprise 维度过滤。
- **影响**：任意员工（含自助注册）可遍历 corpid/roomid 拉取全部企业会话存档原文。
- **待确认**：系统是否多租户、是否依赖前端控制。若多租户则为严重越权。
- **建议**：按 `g.current_user` 强制注入数据范围（超管放行；企业/员工仅限本企业/绑定 sender）。

### [ ] A4. 默认超管弱口令 + 日志明文 ✅🔴
- **位置**：`auth/db.py:69-73`
- **问题**：表为空时创建 `admin / admin123`（ROLE_SUPER_ADMIN），且 `logger.info("已创建默认超管账号: admin / admin123")` 明文打印。
- **影响**：知道项目的人可用默认口令登录拿超管；日志可读者获取凭证。
- **建议**：首次部署强制随机密码并要求首登改密；删除日志明文；禁弱口令。
- **注**：仅"表为空时"创建，生产可能已改密——需确认。

### [ ] A5. 短信验证码可在线爆破 → 账号接管 ⚠️🟠
- **位置**：`auth/db.py:601-621` `verify_sms_code` + `auth/api.py:682-758`
- **问题**：验证失败不消耗验证码、不计数、不锁定、无频率限制；6 位纯数字、TTL 300s；且发送新码不失效旧码，可同时存在多条有效码。`forgot-password`/`register` 校验失败仅返回 400。
- **影响**：发一次码后 300s 内遍历 000000–999999 可命中，重置任意账号密码（重置无需旧密码）。
- **建议**：验证码加 attempts 计数，失败 N 次作废；verify 端点按手机号/IP 限频；发新码时失效同手机号同用途旧码；缩短 TTL。

### [ ] A6. 其他安全收敛项 🔍🟡
- 全局配置读写无角色校验：`get_config`(api.py:2748) 返回全部 insurance_config（含 baidu/钉钉密钥明文），`update_config`(2759) 可写任意 key → 应限超管/脱敏。
- 钉钉目标、监控配置、字段映射管理端点均无角色校验（`api.py:3267/4186/3195` 等），监控配置 create/update 可改历史记录 enterprise_id 归属（数据接管）。
- `get_stats` 缓存 key 只含 query_string、不含用户身份 → 跨企业串统计数据（`api.py:1259`）。
- `rescan_history`(api.py:4397) 无角色校验，可触发全企业 365 天重扫（资源型 DoS）。
- list/批量端点 page_size 无上限（`api.py:303`）→ 内存 DoS。
- token 支持 URL `?token=` 传递 + JWT 7 天无法吊销/改密不失效（`auth/decorators.py:23`、`jwt_utils.py:16`）。
- 用户枚举：`send-reset` 对未注册号返回 404（`api.py:655`）。
- `web/api.py` 运维接口（`/api/fetch`、`/api/contacts/update` 等）仅登录可访问，无角色限制。
- token 泄漏 / SMS 未配置时明文打印验证码（`auth/sms.py:31`）。

## 🟠 二、数据完整性

### [ ] B1. 保单号被静默篡改（影响所有保单）✅🟠
- **位置**：`insurance/policy_parser.py:3617-3632`（配合 `_is_doubled_token` 3606）
- **问题**：PDF 双层文字去重，行级触发用 `any()`（文档却说"超过一半"），且**纯数字串**也满足 doubled 判定被抽稀。
- **实测**：`保单号 1122334455` → `保单号 12345`；`88990011` → `8901`。任何"相邻两位两两相等"的保单号/发动机号被抽掉一半，改后仍是合法数字极难发现。
- **建议**：`_is_doubled_token` 排除纯数字 token（双层文字现象仅针对中文表单值，应要求 token 含 CJK 字符）；行级触发改为真正的"多数 token 为 doubled"。

### [ ] B2. 拉取失败仍推进游标 → 永久丢消息 ⚠️🔴
- **位置**：`core/fetcher.py:69-77`（`save_message` 吞异常见 `storage/db.py:186-215`）
- **问题**：`for item: _process_item(item); seq=item.seq` 无论单条成功失败都推进 seq，批次结束 `update_seq` 推到最后一条。`_process_item` 解密/入库失败仅 return，`save_message` 用 try/except 吞异常 + `INSERT IGNORE`。
- **影响**：失败消息永久跳过，下次从更大 seq 拉，会话存档静默不完整且无感知。
- **建议**：只提交到最后一条**成功**的 seq；或失败 seq 入死信表重试；`save_message` 失败应向上抛阻止游标推进；区分"重复"与"真错误"。

### [ ] B3. seq 列用 INT，企微 seq 是 uint64 ⚠️🟠
- **位置**：`storage/db.py:65`（messages.seq INT）、`storage/db.py:83-88`（cursor_state.seq INT）；SDK 为 `c_uint64`（`finance_sdk.py:47`）
- **影响**：长期运行 seq 超 21 亿溢出报错（被 B2 吞 → 丢消息）或游标卡死。
- **建议**：改 `BIGINT UNSIGNED`。

### [ ] B4. 保单主表/关联表弱一致 🔍🟠
- **位置**：`insurance/db.py:971-977` `save_insurance_record`（`update_insurance_record` 1067-1070 同样）
- **问题**：`_insert_policy_fields` 失败仅 warning 不回滚，主表仍 commit。
- **影响**：`insurance_policy_fields` 缺行，按车牌/人名互补、险种/日期筛选漏该记录。
- **建议**：关联表失败整体 rollback 并抛错；或确认后台回填（db.py:610-637）是否覆盖此场景。

### [ ] B5. upsert 保单号 check-then-insert 竞态 🔍🟡
- **位置**：`insurance/db.py:1737-1789` `upsert_insurance_record_by_policy`（跨两个连接、无事务无锁）
- **影响**：手动重识别 + 自动识别并发同保单号 → 产生重复记录（保单号无唯一约束）。
- **建议**：去重列加唯一索引 + `INSERT ... ON DUPLICATE KEY UPDATE` 或应用层锁。

## 🟡 三、功能逻辑 Bug

### [ ] C1. 按人名正向互补几乎完全失效 ✅🟠
- **位置**：`insurance/handler.py:1072-1084`
- **问题**：缩进错误。`for rec in history:` 循环体只有 1074 一行，循环结束 `hist_fields` 只剩**最后一条**记录；其后 `if isinstance(hist_fields,str)` 在 `for field` 层级，而 `parsed_fields` 正常是 dict 不是 str → **整段补充逻辑不执行**；`break` 也错误退到字段循环（第一个字段处理完即退出）。
- **影响**：无车牌保单的人名正向互补基本失效。
- **建议**：把 1075-1084 缩进进 `for rec in history` 循环体内，与 1074 对齐；修正 break 层级（找到值后 break 内层 rec 循环，继续下一个 field）。

### [ ] C2. 紫金保单号前缀永远被识别成安盛天平 ✅🟡
- **位置**：`insurance/policy_parser.py:318` 与 `320`
- **问题**：`(r'^29104', "安盛天平...")` 和 `(r'^29104', "紫金...")` 重复，顺序匹配 + break，紫金那条不可达。
- **影响**：仅当走到"方式4 保单号前缀兜底"且保单号 29104 开头的紫金保单被误判（紫金保单通常文本含全称走方式2，实际影响较小）。
- **待确认**：29104 前缀到底属安盛天平还是紫金（注释冲突）。两家若共用前缀则前缀法无法区分，应删一条并靠域名/电话区分。

### [ ] C3. 中文大写金额"亿+万"进位错误 ✅🟡
- **位置**：`insurance/policy_parser.py:2704-2722` `_parse_chinese_amount`
- **问题**：`万`/`亿` 分支用 `wan_total = total` 覆盖而非累加，且算"万"段未计入已结算"亿"段。
- **实测**：`壹亿贰仟万` 返回 20,000,000（应 120,000,000）。
- **影响**：跨"亿+万"两级的大写金额错误；且 `_extract_premium` 末尾大写交叉验证（约 3017）会用错误大写值覆盖正确小写值。普通车险极少到亿级，影响小。
- **建议**：改为分段累加（section 乘对应单位后 `result +=`）。

### [ ] C4. quote VIN 正则 `\b` 边界在中文相邻时失效 ✅🟠
- **位置**：`quote/matcher.py:31`（`_VIN_PATTERN = \b[A-HJ-NPR-Z0-9]{17}\b`）
- **问题**：Python Unicode 模式下中文属 `\w`，中文与 VIN 之间无 `\b`。
- **实测**：`车架号LFV2A21K9N3012345`（VIN 紧贴中文）匹配返回 None，VIN 漏识别。
- **建议**：改 `(?<![A-HJ-NPR-Z0-9])[A-HJ-NPR-Z0-9]{17}(?![A-HJ-NPR-Z0-9])`。

### [ ] C5. quote 身份证反面就近错配到他人 🔍🟡
- **位置**：`quote/matcher.py:155-189` `add_idcard_back`
- **问题**：找不到"有正面无反面"的条目时退化为塞进 `entries[-1]`，可能错挂到无关人。
- **影响**：身份证有效期等信息张冠李戴，提交错误数据。
- **建议**：找不到合适正面时暂存到 `_pending_backs`，不强行归入最后一套。

## 🟢 四、健壮性 / 并发

### [ ] D1. 钉钉同步成功误判 → 数据静默丢失 🔍🟠
- **位置**：`insurance/dingtalk_sync.py:366-369`（`append_invoices` 硬编码返回 success=True，更新批次失败仅 print）+ `handler.py:1588`
- **影响**：更新批次全失败也返回成功 → 标记 `dingtalk_synced=1`，钉钉表实际未更新，且后续反向 resync 被误导，数据静默丢失。
- **建议**：更新批次失败累计错误反映到返回值/抛异常；`dingtalk_synced` 仅在确有成功写入时置 1。

### [ ] D2. 钉钉去重 key 错配 + 每条重建服务限流 🔍🟠
- **位置**：`dingtalk_sync.py:294,327,343`（去重 key 默认"保单号"，但映射后列名可能不同）+ `handler.py:1579`（每条记录 new 服务、重新 gettoken）

### [ ] D3. 火山 OCR 熔断逻辑错误 + 无锁并发 🔍🟠

### [ ] D5. 内存队列重启/满载丢消息 🔍🟡

- **问题**：纯内存 `queue.Queue`，进程重启/崩溃/OOM 时未处理消息全丢，满载（已调至 1000）也直接丢弃，无持久化/补偿。

## 已核查确认为「非 bug」（避免重复审查）
- **SQL 注入**：全模块未发现可利用注入。动态 `IN (%s,...)` 为占位符拼接、动态 set_clause/列名均走白名单、排序字段经白名单映射，用户输入一律 `%s` 绑定。
- **连接池泄漏**：各处 `conn = pool.connection()` 后均 `try/finally: conn.close()` 归还，未发现泄漏。
- **ctypes 内存**：`finance_sdk.py` 的 NewSlice/FreeSlice、NewMediaData/FreeMediaData 均在 finally 释放，`GetOutIndexBuf` 返回 c_char_p 自动拷贝后再 Free 安全。
- **JWT**：`algorithms=["HS256"]` 显式限定，无 alg=none/算法混淆；密钥随机生成并持久化，无硬编码弱密钥。
- **密码哈希**：werkzeug pbkdf2:sha256 加盐 + 常量时间比较，无明文/弱哈希/时序问题。
- policy_parser 大量 `lines[i+1]`/`lines[j]` 访问均有边界保护；`re.search().group()` 均先判空；`_extract_premium` 的 `float()` 入参受限捕获组不会抛异常。
