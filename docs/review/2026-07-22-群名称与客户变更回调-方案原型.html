企业微信「群名称 / 外部联系人」变更事件回调 —— 接入方案

参考 wuhuApi 项目 change_external_chat / change_external_contact 事件回调实现方式整理 · 2026-07-22

1现状调研结论

  • wxbot 当前 callback/server.py 只识别 msgaudit_notify（会话存档通知）一种事件，没有接入企业微信「通讯录/客户联系」事件回调；其余事件类型会被静默忽略。
  • 群名维护依赖 task_group_sync.py 定时轮询（覆盖式刷新 wecom_groups 表），客户昵称维护依赖 task_contact_sync.py 定时轮询（10分钟增量 + 6小时全量，刷新 wecom_contacts 表），**都不是事件驱动**，存在分钟级延迟。
  • 企业微信没有单独的「群名称修改」事件：群信息变化统一走 change_external_chat（ChangeType=create/update），只给 ChatId，不带具体改了哪个字段，需要收到通知后主动拉一次群详情比对。
  • wuhuApi 项目在 wuhu.py（约4.69万行）中已实现同类回调：函数式验签解密（与 wxbot callback/crypto.py 的 WXBizMsgCrypt 类逻辑等价）+ change_external_chat / change_external_contact 双事件分流 + BackgroundTasks 异步落库，可直接参考其事件分发方式，**不需要照搬其整套实现**（wxbot 现有封装更完整）。
  • wxbot 已有 storage/group_db.py（wecom_groups）、storage/contact_db.py（wecom_contacts）两张「权威名称表」，均已具备 sync_status/fail_count/name_updated_at 字段设计，可直接复用其更新函数。

2已确认的范围与决策

✓监听范围：全量群，不局限于保单识别监控群。
✓同时覆盖外部联系人（客户）变更事件（新增 / 修改 / 删除），与群变更共用一套回调入口。
✓新增「变更历史」记录表（审计追溯用，当前系统里不存在同类表）。
✓保留现有定时轮询作兜底，与事件回调并存、互不冲突；轮询频率不变。

5数据表设计：wecom_change_history

群变更和客户变更共用一张历史表，靠 entity_type 区分，避免建两张结构相同的表。

CREATE TABLE wecom_change_history (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  entity_type VARCHAR(16) NOT NULL          -- 'group' / 'contact'
    COMMENT '变更实体类型',
  entity_id VARCHAR(128) NOT NULL           -- roomid / external_userid
    COMMENT '实体ID',
  corpid VARCHAR(64) DEFAULT ''             COMMENT '企业ID',
  change_type VARCHAR(32) NOT NULL          -- name_change/create/add_external_contact/
    COMMENT '变更类型',                      -- del_external_contact/del_follow_user 等
  old_value VARCHAR(256) DEFAULT ''         COMMENT '变更前值（如旧群名/旧昵称）',
  new_value VARCHAR(256) DEFAULT ''         COMMENT '变更后值',
  raw_event TEXT                            COMMENT '原始回调事件JSON，便于排查',
  event_time DATETIME DEFAULT CURRENT_TIMESTAMP COMMENT '事件发生时间',
  KEY idx_entity (entity_type, entity_id, event_time)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci
  COMMENT='企业微信群/客户变更事件历史（回调驱动，审计追溯用）';

6事件分发核心逻辑（伪代码）

# callback/event_callback.py
def receive_event_callback():
    xml = crypto.decrypt_msg(...)
    event_type = xml.get('Event') or xml.get('InfoType')  # 兼容两种命名
    change_type = xml.get('ChangeType')

    if event_type == 'change_external_chat' and change_type in ('create', 'update'):
        chat_id = xml['ChatId']
        threading.Thread(target=_handle_group_change, args=(chat_id, change_type)).start()

    elif event_type == 'change_external_contact':
        external_userid = xml['ExternalUserID']
        if change_type in ('add_external_contact', 'edit_external_contact'):
            threading.Thread(target=_handle_contact_change, args=(external_userid, change_type)).start()
        elif change_type in ('del_external_contact', 'del_follow_user'):
            threading.Thread(target=_handle_contact_delete, args=(external_userid, change_type)).start()

    return "success"  # 未识别事件同样返回 success，不影响企微侧重试策略

def _handle_group_change(chat_id, change_type):
    info = contacts_manager._fetch_external_room_info(chat_id)   # 复用现有方法
    old = group_db.get_group(chat_id)
    if not old or old.name != info['name']:
        change_history_db.insert('group', chat_id, change_type, old.name if old else '', info['name'])
    group_db.update_group_success(db, chat_id, corpid, info['name'], info['owner'], info['member_count'], 'external')

7配置变更

# config.yaml 新增
event_callback:
  enabled: true
  path: "/callback/event"
  corpid: "..."
  token: "..."              # 客户联系应用单独申请，与会话存档回调不同
  encoding_aes_key: "..."    # 同上，43位

不复用 extra_callbacks 结构：该配置项语义是"多企业会话存档"（每项对应一套 corpid+secret），而事件回调是同一企业下"客户联系"应用的另一路独立订阅，混用容易在后续排查时产生歧义，单独一个配置块更清晰。

8前置依赖（需要在企业微信管理后台操作，非代码层面）

⚠ 这部分需要你在企业微信管理后台手动完成，无法通过写代码实现：
  1. 为「客户联系」应用单独开启事件回调订阅（外部联系人变更 change_external_contact、客户群变更 change_external_chat 两类事件）
  2. 获取该应用独立的 Token + EncodingAESKey
  3. 配置回调 URL 为 https://你的域名/callback/event，企业微信会先发 GET 请求做 URL 验证
  4. 确认服务器出口/该路径的可信域名校验能通过（与现有 /callback 保持同一域名下即可，无需额外备案）

9兼容性与兜底

  • 不改动 task_group_sync.py / task_contact_sync.py 现有轮询逻辑，事件回调是「实时补充」而非替代。
  • 该功能依赖企业微信 Finance/客户联系 SDK 相关配置，与 callback/server.py 现有回调同属服务器（Linux）专属能力，不需要同步到 run_ocr.py（本地开发入口本就不含微信 SDK 相关模块）。
  • wecom_change_history 是纯新增表，不影响任何现有查询/统计逻辑。

11待确认问题

Q1. 客户改名是否有明确的 ChangeType？
企业微信 change_external_contact 的 ChangeType 目前只有 add_external_contact / edit_external_contact / del_external_contact / del_follow_user / transfer_fail 几种，"改名"会落在 edit_external_contact 里，需要拉详情后与旧值比对才能判断具体改了什么，方案中已按此设计。
Q2. 上方「变更历史查询页面」是否需要现在一起做？
默认先只做后端回调 + 落库，页面作为附加产出；如果你需要，可以在确认本方案后单独排期做前端页面。
Q3. 客户被删除后，wecom_contacts 里的记录要不要保留？
方案默认保留（只在 wecom_change_history 记录一条删除事件），因为同一客户可能被多个员工添加，删除是"某个员工侧"的关系变化，不代表这个人从系统里彻底消失。
