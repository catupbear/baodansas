1需求与现状

需求：客户在群里发「车牌：粤G168T1　业务员：小明　出单渠道：演示渠道」这类文本，系统按车牌把信息回填到保单记录。现在支持哪些关键词、填到哪个字段，全部写死在 insurance/policy_quote_fill.py 的 _FIELD_PATTERNS 里，每加一个关键词都要改代码发版。

目标：做一个配置页面（挂到现有字段配置模板体系内），支持：

  • 指定「关键词 → 系统字段」的映射，目标字段可选系统识别字段或自定义列
  • 同一个字段可配多个关键词（别名），如「业务员 / 跟单员 / 经办」都填到同一列
  • 配置完成后一键复制最终的群消息格式模板，直接发给群成员照着填
为什么挂到模板体系？现有 user_field_config 表已支持 global / enterprise / user 三级作用域 + 命名模板 + 员工可见性，列配置、别名、日期格式、公式都存在里面。关键词规则天然是「企业级、随模板走」的配置，复用这套体系零建表成本，且切换模板时规则跟着切。

每条规则的字段说明

控件说明
目标字段（下拉）可选项 = 当前模板「列配置」里的全部列：系统识别字段（承保公司、业务员…）+ 自定义列（业务员#2、政策商业险…）。下拉里标注 系统 / 自定义，选中系统识别字段时弹出覆盖警告（见第⑦节）
关键词（多个）Tag 式输入，回车添加，可删除。匹配时自动兼容分隔符写法：全角冒号「业务员：小明」、半角冒号「业务员:小明」、空格「业务员 小明」、直接相连「业务员小明」以及字间空格「业 务 员」均可命中；分隔空白仅限行内空格、不跨行（防止「业务员：」换行后误吃下一行内容）
值类型（下拉）文本（截止到空格/标点，≤20字）／数字（含小数）／手机号（11位）／百分比（数字+可选%）。决定值的正则捕获方式
启用开关关闭后规则保留但不参与匹配、不出现在复制格式里

3数据结构（不新建表）

复用 user_field_config 表，新增一种 config_type = "group_fill_keywords"，config_key = "rules"，整体存一条 JSON（与 list_columns 的存法一致）：

[
  {
    "target":   "业务员#2",          // 目标字段 key（与列配置的 key 对应）
    "keywords": ["业务员", "跟单员"],  // 多个关键词别名
    "value_type": "text",            // text | number | phone | percent
    "enabled":  true
  },
  {
    "target":   "出单渠道#2",
    "keywords": ["出单渠道", "渠道"],
    "value_type": "text",
    "enabled":  true
  }
]
  • 作用域与其他模板配置一致：超管存 global、企业管理员存 enterprise、员工存 user；随模板名隔离、随「对员工可见」开关下发
  • field_config_db.py 的 CONFIG_TYPES 列表追加 "group_fill_keywords"，即可自动被 get_template_config / save_template_config（模板读写）、模板复制/删除/重命名逻辑覆盖，无需写新的存储代码

4后端 API

接口说明
GET /api/insurance/field-config/group-fill读当前模板的规则列表（内部走 get_template_config），无配置时返回由现有 _FIELD_PATTERNS 转换来的默认规则（仅前端展示参考，不落库）——只有管理员点保存后该企业才切换到新引擎
POST /api/insurance/field-config/group-fill保存规则列表（内部走 save_template_config）。校验：target 非空、keywords 非空且去重、同一 target 不重复、关键词不含正则特殊符号风险（统一 re.escape 处理，无需拒绝）
GET /api/insurance/field-config/fill-targets返回可选目标字段列表 = 当前模板列配置（list_columns ∪ export_columns）里 type != "record" 的列，标注是否自定义列、是否 OCR 系统字段（用于前端覆盖警告）
GET / POST /api/insurance/config/fill-skip-keywords全局跳过关键词黑名单读/存（insurance_config 表），仅 super_admin，详见第⑦节

权限沿用现有字段配置接口的角色判定（super_admin → global / enterprise → 企业 / employee → 个人），不新增权限逻辑。

5运行时匹配（policy_quote_fill.py 改造）

1
群消息进入fetcher._check_policy_fill_trigger：仅监控群的文本消息触发；文本命中全局跳过关键词黑名单（第⑦节，「群公告」为默认项）时直接忽略
2
roomid → 企业 →规则（新增）查 monitor_configs（enterprise_id + rooms JSON）反查该群所属企业，再读该企业启用模板的 group_fill_keywords 规则。结果按 roomid 缓存 60 秒（TTL 与 _active_tpl_cache 同款），避免每条群聊消息都查库
3
动态构建正则（新增）每条规则编译为：关键词(逐字 re.escape 后插 \s*) + [:：]? + 值捕获。值捕获按 value_type：数字 (\d+(?:\.\d+)?)、文本 ([^\s，,。、；;]{1,20})、手机号 (1[3-9]\d{9})、百分比 (\d+(?:\.\d+)?%?)。编译结果随规则一起缓存
4
解析判定（逻辑不变）必须「车牌 + 至少命中一条启用规则且该项有有效值」才认定为补充文本，否则当普通聊天忽略。车牌归一化、按 roomid 限定同群同车牌记录、update parsed_fields —— 全部沿用现有 apply_policy_quote
5
双轨制：无配置企业走原代码路径（一行不改）企业没保存过规则时，直接执行现有的 parse_policy_quote_text + _FIELD_PATTERNS 原函数原逻辑——不是"转换成默认规则再走新引擎"，而是新引擎只在「该企业显式保存过规则」时才接管。写死逻辑代码保持原样，紫金宝安等线上客户走的代码路径与今天完全相同、零风险
6
只写「有值」的项（新增约束）客户发送时不必带全所有配置的关键词，缺哪个、哪个没填值，就不处理哪个，详见下方规则表

缺项 / 空值处理规则（即使规则全部启用也按此执行）

客户发送情况处理方式
文本里没出现某个已配置关键词该字段完全不处理，记录里的原值（含 OCR 识别值/历史补充值）保持不动
带了关键词但没填值（如「业务员：」后面是行尾、只有标点，或紧跟下一个关键词）该项视为未填，跳过——不写空值、不清空、不覆盖原有内容
值类型不符（数字类字段填了文字等）正则天然不命中，等同未填，跳过
只有部分关键词有值只回填有值的那几项，其余不动（部分更新，不是整体替换）
实现要点：① 值捕获正则本身要求至少 1 个有效字符，「关键词：」后无内容天然不匹配；② 文本类值按行内捕获（不跨行），并在解析前把「其他已配置关键词」作为截止边界，避免「业务员：出单渠道：演示」这类同行粘连时把下一个关键词误当成值；③ 写库前统一过滤：fill = {k: v for k, v in parsed.items() if v and v.strip()}，空串/空白一律剔除后再 update parsed_fields（复制格式冒号后留空，不存在占位符残留问题）。

6一键复制发送格式

纯前端实现，不需要接口。点击「📋 一键复制发送格式」按启用规则生成文本并写入剪贴板（navigator.clipboard，失败降级 document.execCommand('copy')，与页面现有复制逻辑保持一致）：

车牌： 业务员： 出单渠道： 商业：
  • 第一行固定为「车牌：」（车牌是匹配主键，必填），不带示例车牌（已确认）
  • 每条启用规则取第一个关键词作为行首标签，冒号后留空，群成员直接在每行后补值即可
  • 值为空的行（成员没填的项）按第⑤节规则自动跳过，不会写空值
  • 复制成功后 toast 提示「已复制，可直接粘贴到群里让成员照格式填写」

7全局跳过关键词（黑名单，内部管理员维护）

文本中只要包含任一跳过关键词，直接不进入回填解析（当普通聊天忽略）。全局生效（所有企业、所有群），仅内部管理员（super_admin）可编辑。

存储

  • 与模板体系无关，存 insurance_config 表（现有全局配置表，监控群等配置同款），key = group_fill_skip_keywords，value 为 JSON 数组：["接龙", "撤回了一条消息"]
  • 现有写死在 fetcher.py:383 的「群公告」过滤原样保留、不迁移；黑名单是在其后叠加的一道过滤（默认空数组 = 行为与现在完全一致），避免动线上已验证的拦截逻辑

配置入口

放在 /insurance 页现有「设置管理」区新增一张卡片「群内补充 · 跳过关键词」：Tag 式输入 + 保存，仅 super_admin 角色可见（沿用设置区现有权限判定）。

设置管理 — 仅内部管理员可见
🚫 群内补充 · 跳过关键词（全局生效）
群消息文本包含以下任一关键词时，直接跳过关键词回填处理（所有企业生效）
群公告 × 接龙 × 撤回了一条消息 × + 添加

运行时判定位置

  • 在 fetcher._process_item 现有「群公告」过滤处改为读黑名单（内存缓存 60s，与规则缓存同款），命中则 return —— 即同时跳过保险报价、政策回填、台账导出三条关键词链路，与现在「群公告」的拦截范围一致
  • 普通存档不受影响：消息照常入库，只是不触发关键词功能
注意：黑名单是「包含即跳过」的子串匹配，配置过于宽泛的词（如单字「保」）会导致正常补充文本被误跳过。保存时校验：≥2 字、去重、上限 50 个。

8兼容性与风险控制

风险点处理方式
覆盖 OCR 识别值目标字段选中「业务员」「出单渠道」等 OCR 系统字段时，前端弹确认框：「该字段是保单识别字段，群内补充会覆盖识别结果，建议改用自定义列（如 业务员#2）」。允许坚持选择（有客户就是想覆盖），但默认引导到自定义列 —— 延续 afd60c0 那次「#2 独立字段」的设计原则
关键词误命中聊天① 判定门槛不变：必须同车牌一起出现；② 保存时禁止单字关键词（≤1 字提示过短）；③ 规则正则用 re.escape，用户输入不会破坏正则
跨企业数据串写沿用现有 roomid 限定：只回填触发群所在群的同车牌记录，不同企业同车牌互不影响
存量客户兼容（双轨制）写死逻辑（_FIELD_PATTERNS、「群公告」过滤）原代码原样保留，新引擎仅对「显式保存过规则的企业」生效，黑名单默认空数组——上线当天所有线上客户执行路径与升级前逐行相同；后续哪家企业要用新配置，单独给哪家配置，天然灰度。文十七（企业24）的「业务员/出单渠道只允许手动填写」剔除逻辑在 insurance/db.py 独立生效，不受影响
性能规则 + 编译后正则按 roomid 缓存 60s；未配置企业缓存「使用默认」标记，普通聊天群消息只多一次内存判断
文本先到、保单后到现状限制保持不变（文本早于保单入库则不回填、仅记日志）。如需「暂存待补」属独立需求，本期不做，方案里明确留待后续
