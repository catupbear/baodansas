0本次范围变更（相对 07-22 版本）

＋新增需求：群名同时命中「TZ编号」+「识别群」关键词时，自动检查该群是否已配置到对应企业的识别群监控里，未配置则自动补加。两个触发入口：① 定时任务 task_group_sync.py（已有，检测到群名变化时）；② 本方案新建的群变更事件回调（实时检测群名变化）。
－本期不做：客户联系人变更事件 change_external_contact、wecom_change_history 审计表、变更历史查询页面。这三项是 07-22 版本的原始范围，为了让本次「识别群自动匹配」尽快落地先收窄，事件回调蓝图/验签解密骨架预留了后续直接扩展的空间。

1现状调研结论

  • wxbot 当前 callback/server.py 只识别 msgaudit_notify（会话存档通知）一种事件，没有接入企业微信「通讯录/客户联系」事件回调；其余事件类型会被静默忽略。
  • 群名维护依赖 task_group_sync.py 定时轮询（增量600s / 全量6h，覆盖式刷新 wecom_groups 表），是唯一会写 wecom_groups 的地方；core/fetcher.py 消息处理链路只读群名（ContactsManager.get_room_name），不写库、也没有"群名变化"信号，因此不适合作为触发点。
  • 企业微信没有单独的「群名称修改」事件：群信息变化统一走 change_external_chat（ChangeType=create/update），只给 ChatId，不带具体改了哪个字段，需要收到通知后主动拉一次群详情比对。
  • storage/group_db.py::update_group_success 已经内置"新旧群名对比"逻辑，返回 name_changed 布尔值，本次两个触发点都直接复用这个已有返回值，不用重新写比对逻辑。
  • 识别群监控配置已经是 insurance/monitor_config_db.py 的 monitor_configs 表（而非旧的 insurance_config key-value 结构），天然带 enterprise_id、rooms（JSON数组 [{"id":"wr...","name":"群名"}]）、enabled 字段，无需新建表或加字段。
  • 企业编号「TZ+数字」已有先例：insurance/db.py::get_tz008_enterprise_ids 对 enterprises.enterprise_no 做「去除非字母数字字符 + 转大写」归一化后精确比较，本次沿用同一归一化规则，但抽成通用函数（而非像现有代码一样写死 TZ008）。

2已确认的范围与决策

✓识别群判定规则：群名同时满足「包含字面量"识别群"」+「能提取出 TZ+数字 编号（如 TZ050 / TZ-050）」，两者缺一不满足才触发匹配逻辑。
✓企业匹配：提取到的编号归一化（去符号转大写）后与 enterprises.enterprise_no 同样归一化的值做精确比较。
✓判重范围：只要该 roomid 已出现在该企业名下任意一条 monitor_configs（不论 enabled 与否）的 rooms 里，视为已配置，不重复添加。
✓加入目标：需要新增时，加入该企业下 enabled=1 且 id 最大（最新）的一条 monitor_configs；若企业名下不存在任何配置，则自动新建一条（enabled=1，仅填 name/enterprise_id/rooms，钉钉多维表字段留空待人工在前端补配置）。
✓成功即静默：自动补加成功只记 logger.info，不发钉钉通知（属于正常自动化行为，避免产生噪音）。
✓企业未匹配时自动建"预备群"占位企业：群名命中规则但 TZ 编号在 enterprises 里找不到对应企业时，不再只是告警跳过，而是自动创建一条占位企业记录（name="预备群"+提取到的编号，如 预备群TZ055；enterprise_no 存带横杠三位补零格式，如 TZ-055），再继续往下走，把该群加入这个新建企业的识别群配置。
✓建企业动作必须通知：自动建"预备群"占位企业比"往已有配置里加一行"更重大，需要发一条钉钉通知（新增语义化通知函数），提示人工去补充正式企业名称、联系人等信息；而"加入已有配置"这一步本身仍保持静默（只 logger.info）。
✓触发时机：只在群名变化时触发（新群首次写入 / 已有群改名），不对每条群消息做检测，避免高频群产生不必要的数据库/匹配开销。

4新增能力：识别群自动匹配（核心逻辑）

新文件 insurance/auto_monitor_match.py，对外只暴露一个函数，两个触发点都调用它：

# insurance/auto_monitor_match.py
import re

_TZ_PATTERN = re.compile(r'TZ-?(\d+)', re.IGNORECASE)

def check_and_sync_group(db, roomid: str, name: str, corpid: str = ""):
    # 1. 关键词 + 编号规则不满足，直接跳过
    if "识别群" not in name:
        return
    m = _TZ_PATTERN.search(name)
    if not m:
        return
    norm_digits = m.group(1).zfill(3)   # 数字补齐3位，TZ55/TZ050 归一到同一编号
    tz_key = "TZ" + norm_digits          # 查询用归一化编号，如 TZ050

    # 2. 按归一化编号查企业（新增通用函数，见组件清单）
    enterprise = auth_db.get_enterprise_by_no(db, tz_key)
    if not enterprise:
        # 2.1 未匹配到企业：自动建"预备群"占位企业，而不是告警了事
        enterprise_no = f"TZ-{norm_digits}"       # 三位补零，横杠格式，如 TZ-050
        placeholder_name = f"预备群{tz_key}"        # 如 预备群TZ050
        eid = auth_db.create_enterprise(db, placeholder_name)
        auth_db.update_enterprise(db, eid, {"enterprise_no": enterprise_no})
        enterprise = {"id": eid, "name": placeholder_name}
        notify_new_enterprise_placeholder(placeholder_name, enterprise_no, roomid, name)
        # 不 return，继续往下走，把这个群加进新建企业的识别群配置

    # 3. 判重：该企业名下任意一条配置的 rooms 里已包含该群则跳过
    configs = monitor_config_db.list_monitor_configs_by_enterprise(db, enterprise["id"])
    if any(roomid in {r["id"] for r in (c.get("rooms") or [])} for c in configs):
        return

    # 4. 选目标配置：enabled=1 且 id 最大；没有则新建
    enabled = [c for c in configs if c.get("enabled")]
    target = max(enabled, key=lambda c: c["id"]) if enabled else None

    if target:
        rooms = (target.get("rooms") or []) + [{"id": roomid, "name": name}]
        monitor_config_db.update_monitor_config(db, target["id"], {"rooms": rooms})
    else:
        monitor_config_db.create_monitor_config(db, {
            "name": f"{enterprise['name']}-自动创建",
            "enabled": 1, "enterprise_id": enterprise["id"],
            "rooms": [{"id": roomid, "name": name}],
        })
    logger.info(f"识别群自动匹配: {name}({roomid}) → 企业{enterprise['name']}({tz_key})")

边界情况说明：

  • 群名里若出现多个 TZ 编号，只取正则匹配到的第一个。
  • 编号匹配与写入统一按数字补齐 3 位（zfill(3)）归一化：群名里的 TZ55 与 TZ050 分别归一为 TZ055/TZ050，查询企业用 TZ+补零数字，写入 enterprise_no 用 TZ-补零数字（如 TZ-055），占位企业名用 预备群TZ+补零数字（如 预备群TZ055）。这样 TZ55 和 TZ055 会归到同一编号、匹配到同一企业，常见的位数书写差异不会再重复建企业。只有数字位数 ≥4 位且存在前导零差异（如 TZ0050 vs TZ050）这种极端写法才会被视作不同编号——实际业务编号为固定三位，不受影响。
  • 本次不修改已有的 get_tz008_enterprise_ids（TZ008专属车牌兜底逻辑），只新增一个通用查询函数，两者并存，避免不必要的重构范围扩大。
  • 自动建企业复用现有 auth/db.py::create_enterprise（唯一现存调用方是后台"创建企业"人工接口 auth/api.py::api_create_enterprise），该函数本身不接受 enterprise_no 参数，所以要紧接着调一次 update_enterprise 补写，与人工创建企业接口的两步顺序保持一致。

6事件回调分发逻辑（伪代码，最小实现）

# callback/event_callback.py
def receive_event_callback():
    xml = crypto.decrypt_msg(...)
    event_type = xml.get('Event')
    change_type = xml.get('ChangeType')

    if event_type == 'change_external_chat' and change_type in ('create', 'update'):
        chat_id = xml['ChatId']
        threading.Thread(target=_handle_group_change, args=(chat_id, EVENT_CALLBACK_CORPID)).start()

    # 本期不处理 change_external_contact，未识别事件同样返回 success
    return "success"

def _handle_group_change(chat_id, corpid):
    contacts = get_contacts_for_corp(corpid)   # 复用 extra_callbacks 已注册的 ContactsManager，不重建
    info = contacts._fetch_external_room_info(chat_id)
    name_changed = group_db.update_group_success(
        db, chat_id, corpid, info['name'], info['owner'], info['member_count'], 'external')
    if name_changed:
        auto_monitor_match.check_and_sync_group(db, chat_id, info['name'], corpid)

7配置变更

# config.yaml 新增（实际已按午虎科技的真实凭证配置，此处仅示意结构）
event_callback:
  enabled: true
  path: "/callback/event"
  corpid: "ww347251b9144b55c2"  # 归属企业：午虎科技（extra_callbacks 已有的企业）
  agent_id: 1000002              # 客户联系应用 AgentId，仅记录用，验签不需要
  token: "..."              # 客户联系应用单独申请，与会话存档回调不同
  encoding_aes_key: "..."    # 同上，43位

不复用 extra_callbacks 结构：该配置项语义是"多企业会话存档"（每项对应一套 corpid+secret），而事件回调是同一企业下"客户联系"应用的另一路独立订阅，混用容易在后续排查时产生歧义，单独一个配置块更清晰。

调研发现一个关键点（本次实际接入才暴露）：「午虎科技」这个企业本身已经在 extra_callbacks 里配置过，main.py 启动时已经为它创建了一份独立的 ContactsManager（用 external_secret 换取 access_token），并通过 web/api.py::register_extra_contacts(corpid, contacts) 注册进模块内的 _contacts_map。event_callback 不应该用自己的 secret 重新建一份 ContactsManager，而是应该按 event_callback.corpid 去 _contacts_map 里找已经注册好的那一份复用——这样 event_callback 配置块里就不需要重复存一遍 secret（避免以后密钥轮换时两处配置不同步）。web/api.py 目前只有 register_extra_contacts，没有对外的 getter，需要新增一个 get_contacts_for_corp(corpid) 小函数供 event_callback.py 调用。

8前置依赖（需要在企业微信管理后台操作，非代码层面）

⚠ 这部分需要你在企业微信管理后台手动完成，无法通过写代码实现：
  1. 为「客户联系」应用单独开启事件回调订阅（客户群变更 change_external_chat）
  2. 获取该应用独立的 Token + EncodingAESKey
  3. 配置回调 URL 为 https://你的域名/callback/event，企业微信会先发 GET 请求做 URL 验证
  4. 确认服务器出口/该路径的可信域名校验能通过（与现有 /callback 保持同一域名下即可，无需额外备案）

9兼容性与兜底

  • 不改动 task_group_sync.py / task_contact_sync.py 现有轮询逻辑，事件回调是「实时补充」而非替代；task_group_sync.py 只在 name_changed 分支内追加一次函数调用，不改变原有轮询周期和写库逻辑。
  • 该功能依赖企业微信客户联系应用相关配置，与 callback/server.py 现有回调同属服务器（Linux）专属能力，不需要同步到 run_ocr.py（本地开发入口本就不含微信 SDK / 事件回调相关模块，task_group_sync.py 也是独立进程脚本，不在 run_ocr.py 范围内）。
  • insurance/auto_monitor_match.py、get_enterprise_by_no、list_monitor_configs_by_enterprise 均为纯新增函数，不改动任何现有函数签名，不影响现有识别群配置的增删改前端页面逻辑。
  • 本期不建 wecom_change_history 审计表，若后续需要补上客户变更事件/历史留痕，可在本方案的事件回调蓝图基础上直接扩展 change_external_contact 分支，无需重新搭骨架。
