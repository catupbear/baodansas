一、需求背景与设计定位

客户（文十七科技-TZ014 群）提出：前海保司的交强险费用比例，取决于是否带驾乘险出单：

  • 带驾乘险出单：交强险比例 22%，驾乘险比例 30%
  • 不带驾乘险出单：交强险比例 20%

类似需求未来会不断出现（不同保司、不同条件、不同比例），需要做成前端随时可配置、可调整、可批量导入、可总览的通用能力。

设计定位（已确认的方向） 这里只设置比例，不碰计算公式：新增一层「比例规则」，按条件算出一个比例字段的值（如「应付费率」= 0.22 或 0.20）；计算仍走现有普通公式（如 应付费用 = 保费 × 应付费率），公式只需配一次、永远不用改。运营日常只维护比例数字，不接触公式。

2.3 缺口

现有系统无法表达本需求，卡在两点： ① 比例目前要么写死在公式里（保费 × 0.95），要么按「保司+险种」拆多条公式，无法按「是否带驾乘险」「保费金额区间」等条件取不同比例；
② 「是否带驾乘险」是跨保单条件（交强险保单 PDF 里没有驾乘险信息，驾乘险是同车的另一张保单），需要查关联记录才能判断。

三、方案设计：比例规则层（公式引擎零改动）

核心思路 在公式计算之前插入一层「比例规则」：按「保司 + 险种」命中规则后，顺序检查条件分支，第一个满足条件的分支比例生效（都不满足走默认比例），把结果作为一个比例字段（如「应付费率」）注入记录；现有 evaluate_formula() 本来就是按字段名替换数值，普通公式 保费 × 应付费率 照常求值——公式引擎一行不改。

3.1 数据结构（新增 config_type='ratio_rule'，存现有表）

// 一条比例规则（前海交强险案例）——存 user_field_config，config_type='ratio_rule'
{
  "key": "应付费率:前海:交强险",               // 比例字段 : 保司 : 险种（沿用现有三段 key 与匹配逻辑）
  "value": {
    "branches": [                              // 条件分支，自上而下首个命中生效
      {
        "conditions": [                          // 条件组，多条之间为 AND
          { "type": "related",                   // 跨保单条件
            "match_by": "车牌号",
            "policy_type": "驾乘险",
            "op": "exists",
            "days": 7 }
        ],
        "value": 0.22,                          // 命中时的比例
        "note": "带驾乘险出单"
      }
    ],
    "default": 0.20                            // 默认比例（else）
  }
}

// 普通公式保持现状，只需配一条（甚至可配"全部:全部"通用）：
{ "key": "应付费用:全部:全部", "value": { "display": "保费 × 应付费率" } }

3.2 计算时序

在 apply_user_config_to_fields()（insurance/field_config_db.py:1499）内，套用公式之前先执行 apply_ratio_rules()：命中的比例写入 fields["应付费率"]。比例字段同时可作为导出列显示（运营能直接看到每单用的比例，便于核对）。没有命中任何比例规则的记录，比例字段为空，公式行为与现在缺字段时一致（按 0 处理）。

3.3 批量导入比例

客户往往一次给出整张费率表（几十个保司 × 险种 × 条件的比例）。在「比例规则」页签提供「批量导入」：直接粘贴 Excel 区域（Tab 分隔）或上传 CSV，一次生成全部规则。

表格列（5 列）说明与写法
① 比例字段比例写入哪个字段，如 应付费率、结算费率（公式里引用的名字）
② 保司保司简称，全部 表示不限
③ 险种险种简称，全部 表示不限
④ 条件留空或「默认」= 默认比例；带驾乘险 / 不带商业险 = 关联单条件（同车牌 7 天内存在/不存在）；保费>5000、使用性质=营运、承保险种包含摩托 = 字段条件
⑤ 比例22% 或 0.22 均可，自动归一化为小数 0.22
  • 自动合并分支：同一（比例字段, 保司, 险种）的多行自动合并为一条规则——带条件的行按顺序成为分支，「默认/空条件」行成为默认比例；只有一行且无条件的即固定比例。
  • 导入预览：解析后先预览生成的规则与分支结构（错误行标红），确认后才写入；与已有规则 key 重复时可选「覆盖 / 跳过」。
  • 实现位置：纯前端解析（field_config.html 批量导入弹窗），生成规则 JSON 后走现有 buildConfig() / 保存接口，后端零改动。

3.4 规则总览

「比例规则」页签默认即总览视图：按当前模板列出所有规则，一行行展示「比例字段 / 保司 / 险种 / 条件 → 比例」，支持搜索与按保司筛选，点击行内「编辑」进入该规则的分支编辑。运营随时能一眼看清目前每个保司在什么条件下用什么比例。

四、条件类型详解

条件类型分期说明示例
字段条件
type=field		 P1 对本条记录的任意字段做比较。操作符：等于 / 不等于 / 包含 / 不包含 / 大于 / 大于等于 / 小于 / 小于等于 / 为空 / 不为空。数值比较自动提取数字（复用 evaluate_formula 的清洗逻辑）。 「承保险种 包含 驾乘」
「保费 > 5000」
「使用性质 等于 营运」
关联单条件
type=related		 P2 查同企业下的其他保单记录是否存在：按「车牌号 / 车架号 / 投保人」关联，限定险种（可选保司），出单时间前后 N 天内（默认 7 天）。操作符：存在 / 不存在。这是「带驾乘险出单」的关键能力。 「同车牌 7 天内 存在 驾乘险」
「同车架号 存在 商业险」

4.1 关联单条件的实现要点（P2）

  • 已有先例可复用：insurance/db.py:1425-1496 的 find_commercial_compulsory_start_dates / end_dates 已实现「按车牌跨记录查另一险种」的同款查询（用于"交强与交商起保/终保时间"计算字段），SQL 模式直接照搬。
  • 批量预取防 N+1：列表/导出是批量渲染，逐条查库会拖垮性能。做法：应用比例规则前先扫一遍本批记录，收集所有分支需要的（关联键, 险种）组合，一次 SQL IN 查询预取成 set，逐条判断时纯内存命中。
  • 时序问题：交强险先入库、驾乘险后入库时，交强险那条的比例会在驾乘险入库后的下一次查询/导出时自动更新——比例与公式都是展示/导出时实时计算的，不落库，天然解决时序问题。

七、兼容性与风险

项说明
现有公式 / 模板公式引擎与现有 fee_formula 完全不动；未配置比例规则的企业行为零变化。比例规则是纯增量配置类型。
Excel「活公式」导出比例字段作为静态数值列写入导出表；普通公式仍照现状转 Excel 活公式（如 =IFERROR(保费列*费率列,0)），引用比例列即可——活公式能力不受影响，且比例在表里可见、可手改重算，比之前"分支公式降级为静态值"的方案更好。
比例字段命名保存时校验：比例字段名不得与系统既有字段（保费、车船税等）重名，避免注入时覆盖真实数据。
关联条件性能批量预取（一次 IN 查询）替代逐条查库；insurance_records 已有索引，必要时对车牌字段加索引。
关联误匹配同车牌历史续保可能误命中 → 「前后 N 天」时间窗限制（默认 7 天，可配）；车牌为空的记录关联条件直接判否。
配置错误兜底前端保存时强制要求默认比例；万一规则未命中，比例字段留空，公式按缺字段 0 处理，与现有行为一致。
历史 API 兼容API 请求/响应结构不变（比例只是多一个普通字段值）；仅模板配置的保存/读取多识别一种 config_type，老版本前端忽略该类型不受影响。

九、前海案例的最终配置效果

P2 上线后，运营配置如下（公式一条 + 比例规则两条，或直接批量导入三行表格），全程无需开发介入：

配置内容
普通公式（一次性）应付费用 = 保费 × 应付费率（全部保司 : 全部险种，配一次不再改）
比例规则 ①应付费率 : 前海 : 交强险 —— 条件分支：同车牌 7 天内存在驾乘险 → 22%；默认 → 20%
比例规则 ②应付费率 : 前海 : 驾乘险 —— 固定比例 30%

后续任何保司的费率调整：在规则总览里搜到对应行改个数字，或整表批量导入覆盖，保存即生效。

方案小结 只加一层「比例规则」：按条件（本单字段 / 是否带某险种）取出比例数字注入比例字段，计算仍走现有普通公式，公式引擎与现有配置零改动、零迁移；配套批量导入（整表费率一键导入）与规则总览（随时查看每个保司在什么条件下用什么比例），全部前端可配、保存即生效。
