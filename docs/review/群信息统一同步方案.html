一现状问题：群名来源分散，数据杂乱

目前「群名」在系统里有 4 个各自为政的来源，没有唯一权威数据，导致同一个群在不同页面显示不一致、群改名不更新、解析失败后前端裸显 roomid（如 wrmjPuGQAAG7ZXa6qsQ_...）：

#来源使用位置问题
1 contacts_cache 表
（通讯录永久缓存）		 监控配置页群列表
（/api/insurance/rooms）、消息监控页		 永久缓存从不刷新：群改名不更新；解析失败写死 __unresolvable__ 标记后不再重试
2 insurance_records.room_name
（保单入库时固化）		 台账列表每行记录的「群名」列、导出 Excel 入库那一刻的快照，之后永不回填；当时解析失败就永远是空
3 insurance_config 监控配置里存的 {id, name} 台账列表「群名」筛选下拉
（/api/insurance/monitored-rooms）		 配置保存那一刻的快照；有的配置只存了 id 没存 name，前端要再补两次解析请求
4 前端现场调 /api/contacts/resolve 兜底 台账下拉加载时 页面每次加载都可能触发 API 调用，慢且结果又写回 contacts_cache（回到问题1）
目标：建立一张统一的群信息表作为全系统唯一权威来源（Single Source of Truth），由一个独立的定时任务（类似 wuhuApi 的 task.py）负责拉取和刷新，所有读群名的地方共用这张表。

二整体架构

群清单来源①：messages 表 DISTINCT roomid（会话存档出现过的群）
群清单来源②：企微客户群列表 API（可选，发现还没发过消息的新群）
↓
独立定时任务 task_group_sync.py（类似 task.py，独立进程 + schedule）
逐群调企微 API：存档接口 → 客户群接口 → 跨企业降级
↓ 写入
统一群信息表 wecom_groups（唯一权威来源）
roomid · corpid · 群名 · 群主 · 成员数 · 同步状态 · 同步时间
↓ 共用（只读）
① 监控配置页群列表（/api/insurance/rooms）
② 台账筛选下拉（/api/insurance/monitored-rooms）
③ 台账列表每行群名（查询时 JOIN，room_name 仅作历史兜底）
④ 消息监控页 / 导出 Excel / 失败群通知
核心思想和 wuhuApi 的 sync_group_chat_status() 一致：定时全量同步 → 落一张群表 → 业务只读这张表。 区别是 wxbot 是多企业（车物家 + extra_callbacks），且台账里既有内部群也有外部群，所以按「群清单 + 逐群查详情」而不是「单一企业客户群列表」来取数。

三数据库设计

3.1 新表 wecom_groups

CREATE TABLE IF NOT EXISTS wecom_groups (
    roomid          VARCHAR(128) NOT NULL,        -- 群ID
    corpid          VARCHAR(64)  NOT NULL DEFAULT '', -- 所属企业（解析成功的那个企业）
    name            VARCHAR(256) NOT NULL DEFAULT '', -- 群名（权威值）
    owner           VARCHAR(128) DEFAULT '',      -- 群主 userid（客户群接口可拿到）
    member_count    INT          DEFAULT 0,       -- 成员数
    group_type      VARCHAR(16)  DEFAULT '',      -- internal(内部群)/external(客户群)
    sync_status     VARCHAR(16)  DEFAULT 'pending', -- ok/failed/unresolvable/pending
    fail_count      INT          DEFAULT 0,       -- 连续失败次数（用于退避）
    first_seen_at   DATETIME     DEFAULT CURRENT_TIMESTAMP, -- 首次发现时间
    name_updated_at DATETIME     NULL,            -- 群名最近一次变化时间
    last_synced_at  DATETIME     NULL,            -- 最近一次成功同步时间
    PRIMARY KEY (roomid),
    KEY idx_sync (sync_status, last_synced_at)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4;

3.2 写入规则（保证数据不再杂乱的关键）

情况动作
API 拉到群名，与库里不同更新 name，记 name_updated_at，fail_count 清零，状态 ok
API 拉到群名，与库里相同只更新 last_synced_at
API 拉取失败（超时/无权限）不覆盖旧群名，fail_count += 1，状态 failed；连续失败 ≥ 5 次的群降低同步频率（每天只试 1 次）
企微明确返回「群不存在/已解散」保留最后已知群名，状态 unresolvable，不再高频重试

3.3 与 contacts_cache 的关系

contacts_cache 继续保留，但只负责"人名"（员工/外部联系人/wb机器人）；群名职责整体迁移到 wecom_groups。不删旧数据，读取优先级改为：wecom_groups.name → contacts_cache（过渡期兜底）→ roomid。

四独立定时任务 task_group_sync.py

4.1 形态：独立进程（与 web 服务完全解耦）

  • 仿照 wuhuApi/task.py：独立入口文件 + schedule 库 + while True: run_pending() 主循环，用 systemd / nohup 单独跑一个进程；
  • 崩了、重启、慢了都不影响 web 服务（也解决了之前"拉取会不会影响程序"的顾虑）；
  • 复用 config.yaml（主企业 + extra_callbacks 各企业的 corpid/secret）和 storage/db.py 连接池、core/contacts.py 的 API 调用封装；
  • 用 MySQL 命名锁 GET_LOCK('wxbot_group_sync', 0) 防止误起两个进程时重复同步。

4.2 调度计划

任务频率说明
增量发现 每 10 分钟 把 messages 里新出现、wecom_groups 还没有的 roomid 插入为 pending 并立即解析——新群秒级可见，替代现在 contacts 的 auto_resolve 群名部分
全量刷新 每 6 小时 逐个刷新已有群的群名/成员数（限速 0.3s/次），捕捉群改名；连续失败 ≥ 5 次的群退避为每天 1 次
客户群列表发现（可选，二期） 每天 1 次 照搬 task.py 的 externalcontact/groupchat/list，按企业拉全量客户群，发现"还没发过消息"的新群，配监控群时不用先让群里发消息

# 伪代码：与 core/contacts.py 的 _fetch_room_info 一致的降级链

        name, detail = corp.存档接口(roomid)          # msgaudit/groupchat/get（内部群）

            return corp.corpid, name, detail          # 命中即停

五读取端改造：所有群名共用 wecom_groups

位置现状改造后兼容说明
监控配置页群列表
GET /api/insurance/rooms		 messages DISTINCT + contacts_cache，未命中现场调 API（慢） 直接 SELECT roomid, name FROM wecom_groups（JOIN messages 保持"出现过消息"的范围），不再现场调企微 API，接口毫秒级返回 返回 JSON 结构不变（{rooms:[{id,name,type}]}），前端零改动
台账筛选下拉
GET /api/insurance/monitored-rooms		 群名读监控配置里固化的 name，前端还要两次补解析 群 id 仍来自监控配置，群名一律以 wecom_groups 为准；配置里的 name 字段降级为兜底 返回结构不变；前端可删掉 /api/contacts/resolve 补偿逻辑（也可先留着，无害）
台账列表每行群名
（list_insurance_records）		 读 insurance_records.room_name 固化值 查询时 LEFT JOIN wecom_groups g，取 COALESCE(g.name, r.room_name, r.roomid)——群改名后历史记录同步变新名，无需回填 UPDATE room_name 字段保留不删（历史快照 + 导出兜底 + 搜索仍可用）；模糊搜索群名改为搜 g.name OR r.room_name
监控配置保存
POST /api/monitor-configs		 rooms 存 {id, name} 快照 只存 id（name 可继续存但仅作展示兜底），读时统一查 wecom_groups 历史配置里的旧格式（纯 id 数组 / 对象数组）已有兼容代码，无需迁移
保单入库写 room_name
（insurance/handler.py）		 调 contacts.get_room_name（可能触发 API） 先查 wecom_groups（基本必命中，入库变快）；未命中再走原 API 链路并回写 wecom_groups 写入逻辑不变，只是取名来源前移
兼容原则：所有 API 的 URL、请求参数、返回 JSON 结构全部不变，只改服务端取数来源。老版本前端/导出脚本不受影响；insurance_records.room_name、contacts_cache 均保留，随时可回滚（把 JOIN 去掉即回到现状）。

七对运行中程序的影响评估

维度影响说明
web 服务性能变快同步在独立进程；/rooms 接口从"现场调企微 API"变为纯表查询
企微 API 频控可控0.3s/次限速 + 失败退避；当前几十个群一轮 < 1 分钟；access_token 与 web 服务各自缓存，互不干扰
数据库轻微新表很小（群数量级=几十~几百行）；台账列表多一个按主键 JOIN，可忽略
部署复杂度+1 进程多一个常驻进程需要 systemd/supervisor 托管（与 wuhuApi task.py 同款运维方式）
历史数据无损不删不改 room_name / contacts_cache / 监控配置，全程可回滚

八待确认的问题

  1. 全量刷新频率：默认 6 小时，是否需要更快（群改名多不多）？
  2. 任务形态：确认用「独立进程」（推荐，同 task.py），还是并入 web 服务后台线程（少一个进程但耦合）？
  3. 三期的客户群列表发现：需要企微「客户联系」权限并配置各企业群主可见范围，是否现在就要？
  4. 台账每行群名 JOIN 实时值后，导出 Excel 也会用新群名——历史导出口径变化是否接受？（不接受则导出仍用固化 room_name）
