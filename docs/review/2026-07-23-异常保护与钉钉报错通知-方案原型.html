台账系统 · 异常保护与钉钉报错通知方案

系统方法/API 加异常保护，报错时钉钉通知（含完整 traceback，文案标注"台账系统"）· 2026-07-23

1现状调研结论

  • core/notify.py 已有完整的钉钉群机器人 webhook 推送封装（DingTalkNotifier + notify_error()），全项目约 15 处已手动调用，均在 except 块内、以字符串形式传入 error。
  • 全项目未发现 import traceback 用法，当前无任何地方记录/发送完整堆栈。
  • insurance/api.py:479-482 已有一个 @insurance_bp.app_errorhandler(500)，因非 blueprint-scoped 实际对整个 Flask app 全局生效，但不含 traceback，且 web/api.py、callback/server.py 未见等效兜底。
  • API 响应约定统一为 {"code": xxx, "msg": "..."}（jsonify）。
  • 全项目共 8 处长期运行的常驻 daemon 线程/循环（消息拉取、通讯录同步、保单/AI核对/报价三个队列、超时匹配、补录扫描、看门狗），未见统一定时任务框架，定时任务靠外部 crontab 调用独立脚本。
  • 项目规模约 44 个 .py 文件、700+ 函数（insurance/ 目录占 547 个）——逐个包裹所有内部函数不现实，且会掩盖需要向上传播、由调用方感知的异常。

2总体方案：三层防护

不做"给每个函数加 try"的字面式改造，改为三层防护，异常最终都收敛到同一个增强后的 notify_error()：

①API 层全局兜底——Flask 全局 errorhandler，覆盖 web/api.py、insurance/api.py、callback/server.py 全部路由，不用给每个路由函数加装饰器。
②后台常驻循环逐个保护——8 处长期运行的队列消费者/循环体，每轮/每个任务 try/except，防止一次异常导致整个线程退出。
③定时脚本顶层保护——4 个 crontab 独立脚本的 main() 顶层加保护，避免脚本崩溃后无人知晓。

关键设计取舍：内部函数（如 policy_parser.py 里 50+ 保司的字段提取函数）不做逐个包裹——异常被吞掉会导致调用方拿到不完整数据而不自知，风险比"偶尔崩一次"更大。三层防护只在"最终兜不住"的最外层补网，不改变已有的局部 try/except 和业务降级逻辑（如百度 OCR 兜底、SDK 重试）。

4核心改造：core/notify.py · notify_error() 增强

函数签名不变：notify_error(module: str, method: str, error: str, detail: str = "")，全项目 15 处现有调用完全向后兼容，不用改一行调用代码——只要本来就在 except 块里调用（已确认全部如此），增强后自动带上 traceback。

# core/notify.py（新增部分）
import sys, traceback

tb_text = ""
if sys.exc_info()[0] is not None:          # 仅在 except 块内调用时才有堆栈
    tb = traceback.format_exc()
    lines_tb = tb.strip().splitlines()
    if len(lines_tb) > 40:                  # 截断保护，避免钉钉消息过长
        lines_tb = ["... (已截断，仅显示最后40行) ..."] + lines_tb[-40:]
    tb_text = "\n".join(lines_tb)

5API 层全局异常兜底

# main.py 新增
@app.errorhandler(Exception)
def _handle_uncaught_exception(error):
    logger.error("未捕获异常: %s", error, exc_info=True)
    notify_error("Web服务", request.path, str(error), f"method={request.method}")
    return jsonify({"code": 500, "msg": "服务器内部错误"}), 500
  • 覆盖 web/api.py、insurance/api.py、callback/server.py 所有蓝图路由，返回格式与现有 {"code": xxx, "msg": "..."} 约定一致。
  • 删除 insurance/api.py:479-482 现有重复的 @insurance_bp.app_errorhandler(500)，避免同一异常触发两次通知。
  • 各路由函数内部已有的局部 try/except 保持不变，不受影响——兜底只捕获路由函数内部没接住、意外冒出来的异常。

6后台常驻循环保护（8 处）

给以下循环体补上"每轮/每个任务 try/except 包裹，异常时记录 + notify_error + continue，不让线程退出"（若已有等效保护则跳过，实现阶段逐个确认现状再决定是否需要改动）：

文件函数说明

main.py_stuck_processing_watchdog卡死自愈看门狗
core/contacts.py_worker通讯录同步
insurance/handler.py_consume保单识别队列
insurance/ai_checker.py_consumeAI核对队列

一次性任务线程（do_fetch、批量下载、数据回填等）不在本次强制范围内——通常已有局部 try/except，且一次性失败不会导致常驻服务整体挂掉。

7定时脚本保护（4 个）

renewal_task_scan.py、policy_expiry_reminder.py、task_group_sync.py、task_contact_sync.py 的 main() 顶层加：

if __name__ == "__main__":
    try:
        main()
    except Exception as e:
        logger.error("脚本执行异常: %s", e, exc_info=True)
        notify_error("定时任务", "脚本名.main", str(e))
        sys.exit(1)

9测试计划

  • 单元验证：手动触发 notify_error() 在 except 块内/块外两种场景，确认 traceback 是否正确附加/为空。
  • API 层：本地起服务，构造一个会抛异常的路由，确认全局 errorhandler 捕获、返回 JSON、钉钉收到含 traceback 的通知。
  • 后台循环：本地 mock 一次异常，确认线程不退出、下一轮正常执行、钉钉收到通知。
  • 回归：确认现有 15 处 notify_error 调用点行为不变（仅多了 traceback 字段），15 分钟去重仍生效。
  • run_ocr.py 同步检查：main.py 新增的 errorhandler 需同步确认 run_ocr.py（本地开发入口，无 SDK 但仍有 Flask 路由）是否也需要注册。

10兼容性与边界

不改变：已有的局部 try/except 逻辑和业务侧错误处理/降级逻辑（百度 OCR 兜底、SDK 重试等），三层防护只在"最终兜不住时"的最外层补一道网；不对 insurance/policy_parser.py 等内部字段提取函数逐个包裹，避免异常被吞掉导致调用方拿到不完整数据而不自知。
需注意：gunicorn 多 worker 场景下，每个 worker 会各自运行常驻线程，异常通知可能来自不同 worker，属正常现象，沿用现有进程内去重即可，不做跨 worker 去重。
